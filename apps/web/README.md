# Lorebase web

The web application of Lorebase: Explorer, Canvas, Modeler and Review over the Keeper REST API (docs/design.md, sections 11 and 12). It uses only the public REST API. It runs without a backend in mock mode, and against a real Keeper in live mode (see [Live mode](#live-mode)); the end-to-end tests in `e2e/` drive the built app against Keeper from a compose stack or from the repository.

Stack: React 19, TypeScript (strict), Vite, Tailwind CSS 4, TanStack Router (file-based) and Query, Sigma.js with graphology, CodeMirror 6 and `yaml` for the schema editor, Vitest with Testing Library, Playwright for the end-to-end tests, `openapi-typescript` for the API types.

## Run

Requirements: Node.js 24 and pnpm.

```bash
cd apps/web
pnpm install
cp .env.example .env     # mock mode by default
pnpm dev                 # http://localhost:5173
```

| Script                    | What it does                                                          |
| ------------------------- | --------------------------------------------------------------------- |
| `pnpm dev`                | Vite dev server with HMR                                              |
| `pnpm build`              | Type-check, build into `dist/`, check the bundle budget               |
| `pnpm bundle:check`       | Check `dist/` against `bundle-budget.json`                            |
| `pnpm analyze`            | Build with a size treemap in `node_modules/.cache/analyze/stats.html` |
| `pnpm preview`            | Serve the production build locally                                    |
| `pnpm test`               | Unit and component tests (Vitest, jsdom)                              |
| `pnpm typecheck`          | `tsc --noEmit`                                                        |
| `pnpm lint`               | ESLint (type-aware) and Prettier check                                |
| `pnpm format`             | Prettier write                                                        |
| `pnpm types`              | Regenerate `src/api/generated/keeper.ts`                              |
| `pnpm e2e`                | Playwright flows against a real Keeper                                |
| `pnpm screenshots`        | Regenerate the PNGs in `docs/images/` (mock)                          |
| `pnpm screenshots flow`   | Record `docs/images/tour.gif` (mock)                                  |
| `pnpm screenshots --live` | The same PNGs from a running Keeper                                   |

While iterating, run only the tests that cover what you changed, for example `pnpm test src/features/review`.

## Bundle size

Every screen is a lazy route (`lazyRouteComponent` in `src/routes/`, the screen and its URL binding in `src/features/<area>/*-route.tsx`), and `vite.config.ts` puts the vendor libraries in chunks of their own (`react`, `tanstack`, `graph` for Sigma and graphology, `codemirror`, `yaml`). The Canvas library and the YAML editor load only on the screens that use them. `RouteFallback` shows while a screen loads.

`bundle-budget.json` caps the main chunk (the entry named by `index.html`) and the whole first load (the entry plus its preloaded chunks), raw and gzipped, in kB of 1000 bytes. `pnpm build` fails when a limit is exceeded; raise a limit only on purpose, in the same change that grows the bundle. `pnpm analyze` builds into `node_modules/.cache/analyze/` and writes `stats.html` there to see what a chunk holds.

## Screenshots

`pnpm screenshots` regenerates the pictures used by `docs/tour.md` and the root README. It builds the app in mock mode into `node_modules/.cache/screenshots-dist`, serves it with `vite preview` on a free port, opens each route in Chromium (1440x900, light theme, plus one dark Explorer shot) and writes `docs/images/<screen>.png`. It does not need a backend or a `.env` file.

```bash
pnpm exec playwright install chromium   # once per machine
pnpm screenshots
```

`pnpm screenshots flow` records a scripted walk (Explorer, a Record, Canvas, the Review resolver) with Playwright video and encodes `docs/images/tour.gif` with ffmpeg; without ffmpeg it stitches PNG frames with Pillow through `uv run --with pillow`. Keep the file under 2 MB; the script warns when it is larger. Frame rate, width and palette are in `FLOW.gif`.

`pnpm screenshots --live --keeper http://127.0.0.1:8080` takes the same pictures from the app in live mode (`--keeper` falls back to `LOREBASE_E2E_URL`). The script loads the supply sample under a Domain of its own through the REST API (the loader of the end-to-end tests, `e2e/supply.ts`), prepares a Proposal with two Conflicts, builds the app with `VITE_API_MODE=live` and a same-origin proxy to Keeper, and drops the Domain afterwards (`--keep` leaves it). Keeper must run with authentication off and `keeper.proposals.allow_self_approval: true`, as the end-to-end stack does. The pictures in `docs/images/` are the live ones; without `--live` the mock produces them as before. `tour.gif` is recorded in mock mode only.

**From a running demo stack, read only (the pictures of docs/tour.md).** `pnpm screenshots --live --keeper http://127.0.0.1:8090 --domain supply --guide http://127.0.0.1:8090` uses the existing Domain as it is: nothing is loaded, reviewed, merged or dropped. It builds the current app in live mode, serves it with a same-origin proxy to that Keeper (`/api`) and to the guide service (`/guide`, with the guide's own origin, so its `allowed_origins` need no change), reads the ids it needs (an open extraction Proposal, a guide session) with GET requests, and takes the `DEMO_SHOTS`: Explorer, a Record and its History, the Canvas, the Modeler editors and previews, typo-tolerant and hybrid search in the Retrieval lab, Review with extraction items and schema suggestions, Documents, Explore with a real answer of the guide service (one question; the guide records its trace) and that trace in Agent activity, Settings and the dark Explorer. Then take the pictures a demo stack cannot show from the mock: `pnpm screenshots --only modeler-start,modeler-source-mapping,sources,review-conflict`.

`--only documents,review-items` takes just the named pictures. A failed picture is reported and the others are still taken; the run then exits with an error naming the failures.

The routes, viewport, theme and the browser flags live in the `MOCK_SHOTS`, `LIVE_SHOTS`, `DEMO_SHOTS` and `CONFIG` constants at the top of `scripts/screenshots.ts`. The Canvas needs WebGL 2, so Chromium is started with SwiftShader flags; if a graph does not draw, the script says so and the list fallback is captured instead.

The optional values are non-functional tunables with defaults in `src/config/env.ts`. A missing or invalid required value stops the app at start with a message on screen. `src/config/env.ts` is the only place that reads the environment; components get the validated config from `useConfig()`.

### Runtime configuration

`index.html` loads `/config.js` before the app. The file sets `window.__LOREBASE_CONFIG__`, an object that `withRuntimeConfig` in `src/config/env.ts` overlays on the build environment before validation. The runtime value wins; a key that is missing, empty, of another type or unknown leaves the build value in place. A file that does not set the object, or sets something other than a plain object, is ignored.

Accepted keys:

| Key                                 | Same as                                         |
| ----------------------------------- | ----------------------------------------------- |
| `apiMode`                           | `VITE_API_MODE`                                 |
| `keeperBaseUrl`                     | `VITE_KEEPER_BASE_URL`                          |
| `apiToken`, `token`                 | `VITE_API_TOKEN`                                |
| `guideUrl`                          | `VITE_GUIDE_URL`                                |
| `docsUrl`                           | `VITE_DOCS_URL`                                 |
| any name matching `VITE_[A-Z0-9_]+` | that variable (the tunables in the table above) |

`public/config.js` is an empty object, so `pnpm dev`, `pnpm preview` and the build all serve the file. The `lorebase-web` image is built in mock mode and switches to live mode at run time, either with `docker run -e VITE_API_MODE=live -e VITE_KEEPER_BASE_URL=https://keeper.example.com ...` (its entrypoint writes `/config.js` from the `VITE_*` environment) or with a mounted `config.js`, as the Helm chart does.

A token in `config.js` is readable by anyone who can load the page. Use it for development or a trusted network only; prefer the token typed in Settings, or no token behind a proxy that adds it.

## Mock mode

`VITE_API_MODE=mock` serves two sample Domains from memory: `supply` (Suppliers, Parts, Plants, Contracts; the demo Domain of the glossary) with several Branches, Proposals, Conflicts and extraction items, and `hr`.

The mock is a plain object that implements the same `KeeperApi` interface as the HTTP adapter, not a service worker. Reasons: no extra dependency and no worker file to ship, it runs unchanged under Vitest and in a static build, and it keeps Branch state mutable for the session so Review actions can be tried. What it does:

- Reads: Domains, Branches (with ahead and behind counts against the default Branch), log, schema per Branch, Records with the query DSL (`where` with `and`, `or`, `not`, `via` and `derived`, ordering, cursor paging), Links in both directions, Lineage, history, search, neighborhood, diff between Branches.
- Writes: create and delete Branches, create, review, close and merge Proposals, resolve Conflicts, decide extraction items (staged edits, the re-materialized extraction Branch, the 422 of a Contract without its Link), store and list documents, create Domains, commit schema change sets.
- Merge attempts: Proposal 41 (`model/risk` into `main`) carries six Conflicts of six kinds (`SC1`, `DV1`, `DV2`, `XS4`, `XS5`, `XS9`) and one automatic policy Resolution; Proposal 43 carries one `DV1`. The Conflicts are seeded, not recomputed from the Branches. Resolutions are stored by fingerprint and checked against the Conflict (choice allowed for its kind, `value` or `values` only on `custom`, a value for every member of a group). `POST .../merge` applies them to a copy of the source state, schema changes first, and re-validates custom values against the merged schema: a refused Resolution is dropped and its reason is kept on the Conflict (`details.rejected`). It answers `merged` with a merge Revision (parents: target head, source head) or `conflicts` with the attempt that remains. The target does not change until every Conflict is resolved.
- Schema change sets: `applyChanges` runs the commands on the Branch schema, checks the structural rules (names, references, types, constraints, cardinality, Trait mappings), migrates the stored Records and Links (casts with the safe, checked and forbidden rules, defaults, dropped Attributes and Kinds) and reports the migrations. A checked cast that fails on a stored value, or a new required Attribute without a default, makes the set invalid and commits nothing. A protected Branch refuses a commit (409 `protected-branch`) but answers a dry run. Built-in Operations are generated for new Kinds.
- Inference, Sources and Admin: `schema:infer` answers with the recorded output of the real inference on `examples/supply/data` (the run behind the gold test: 6 of 6 Kinds and keys, 44 of 47 Attribute types, 7 of 7 Relations), narrowed to the tables the request names (file names for CSV, `tables` for Postgres); it does not read the uploaded bytes. Only `secret://env/ERP_DSN` is allowlisted for Postgres. Source runs are sample data, and a sync queues a job that the mock runs at once with nothing new to read. API keys, principals, grants and the audit log are kept in memory; creating or revoking a key, a sync and an inference write audit entries, newest first, with a chained hash.
- Documents and extraction items: the library of `supply` holds the four texts of `examples/supply/documents` (verbatim, so the offsets of the items stay valid), a PDF and a scanned PDF whose job failed. Proposal 44 holds 13 items from those four documents: the first two are the output shown in `docs/extraction.md` (the Contract C-3025 and its `with_supplier` Link), the rest are rule, local-model and chat-model items with an ambiguous match, a rejected item and one accepted at once; Proposal 42 holds four accepted items from the PDF. Deciding items rebuilds the extraction Branch from the accepted ones over the target Branch as it was, so the diff of the Proposal follows the decisions. The sample Contract has a few Attributes more (`start_date`, `annual_value`, `currency`, `incoterm`, `payment_terms_days`) and `main` has the Suppliers, Part and Plants those documents name. A new upload is stored (Markdown and text keep their text for the viewer, a repeated file answers `duplicate`), its job moves from queued to running to succeeded on the next two reads, and it ends with no items: the mock does not extract. URL intake accepts `https://documents.example.test/...` only.
- Explore: the `supply` Domain serves example questions (`domain.examples`) and the panel plays a scripted exploration for each (`src/api/mock/explore.ts`, scripts in `src/api/mock/sample/explore.ts`), one event every `VITE_EXPLORE_MOCK_STEP_MS`, cut to the max steps asked; other questions get a search that finds nothing. "View trace" opens the sample trace session.
- Not emulated, answered with a 501 problem: committing an Operation (dry run works), traversal, Trait queries. Stale merge attempts (target head moved while resolving) are not modeled.

Sample data lives in `src/api/mock/sample/`. To point the app at a real Keeper, see [Live mode](#live-mode); no screen changes.

## API types

Two layers. `src/api/generated/keeper.ts` is the wire layer: types produced from `docs/openapi.json` by `openapi-typescript` (`pnpm types`; the dev dependency is there because the API contract is the single source of truth and hand-copying 90 schemas drifts). It is committed, and `src/api/generated/generated.test.ts` regenerates it in memory and fails when the file is stale, so after `make openapi` run `pnpm types` and commit both files.

`src/api/types.ts` keeps the names the screens use. Where a type maps one to one onto the contract it is an alias of it (`Domain`, `Proposal`, `ProposalDetail`, the review, approval and check types, `CreateBranchInput`, `WhoAmI`, `Webhook`, `ContextPack`, and so on). The rest are UI-facing view models that the adapters produce: `Schema` (lists of elements, types spelled `decimal(12,2)`, see `src/api/live/schema.ts`), `RecordRow` (`Kind/key` references and values by Attribute api name), `Revision`, `Branch` (with its distance to the default Branch), `DiffResponse`, `MergeAttempt` and the Conflict types. The `KeeperApi` interface isolates the screens from both.

## How it fits together

- **Branch is first class.** The Domain is a path segment (`/supply/...`); Branch and Revision are search params (`?branch=model%2Frisk&at=<revision>`) shared by every screen. The top bar shows the Branch switcher with the head Revision and how far the Branch is behind the default Branch. Navigation links carry the context along.
- **Scope.** `ScopeProvider` resolves the Domain and Branch named by the URL and exposes `{domain, branch, head, at}` through `useScope()`. Screens render only when both exist.
- **Revision-aware caching.** Every scoped query key includes the Branch head Revision (or `at`), so a Branch that moves never serves old reads as current.
- **Theme.** Colors are CSS variables in `src/styles.css`, mapped to Tailwind utilities (`bg-surface`, `text-muted`, `border-line`, ...). Light and dark follow the system by default and can be forced from the top bar or Settings; the choice is kept in local storage.
- **Canvas.** Sigma 4 needs WebGL 2. It is loaded on demand; when WebGL is not available (tests, some remote desktops) the canvas shows a message and the list view below still describes the graph. Layout is ForceAtlas2: graphs up to `VITE_CANVAS_PRELAYOUT_MAX_NODES` nodes are laid out before the first draw; larger ones are drawn at once and laid out in a web worker (the supervisor of `graphology-layout-forceatlas2/worker`, loaded with the Canvas), with Barnes-Hut from `VITE_CANVAS_BARNES_HUT_MIN_NODES` nodes. The run stops when the nodes settle or at the time budget, and can be paused and resumed; it is not restarted by re-renders. Large graphs also lose edge labels, most node labels and (while moving) edges. The worker is a blob, so a Content-Security-Policy needs `worker-src blob:`; without workers the graph keeps its pre-layout. `pnpm perf:canvas` measures a generated 5,000 node, 10,000 edge graph.

## Screens

Built with real data from the active adapter: Explorer (Domain home, search with Kind filter, Kind table with sort and paging, Record page with per-value Lineage and a History tab: the changes of the Record, newest first, with before and after values and "Load more"), Canvas (graph explorer, schema graph), Modeler (Kinds, Attributes, Relations, Traits, Operations, Derivations, Sources lists, the schema editor and "Start from data"), Review (Proposal list with Conflict counts, Proposal detail with checks, reviews and approvals, a review form, merge attempt and Conflict resolver, data diff, merge and close, the Items tab of an extraction Proposal, and the Schema suggestions tab), Sources (list, run history, YAML editor), Documents (library, upload, URL intake, document viewer), Settings (appearance, connection and token, who Keeper says you are, Domain and runtime values, and the Admin basics: API keys, principals and grants, audit log), Explore (questions to the optional Guide service, streamed step by step; scripted on the mock, see [docs/guide.md](../../docs/guide.md#the-explore-panel-in-the-web-app)). The top bar has a Branch switcher and a "New Branch" button that starts a Branch at the head of the one on screen.

**Domain-agnostic.** No screen names a Kind, Record or Domain of a dataset, and no description puts the Domain's name into its copy (the Domain is in the top bar). Sample questions come from the schema (`domain.examples`, shown only when present); sample data lives in the mock fixtures (`src/api/mock`) and tests. `src/test/domain-agnostic.test.ts` fails on dataset identifiers or an interpolated Domain name anywhere else.

**Copy.** Every user-facing string is in `src/messages/<area>.ts`: a heading plus at most one short line per screen, longer explanations in the docs behind a "Learn more" link (`VITE_DOCS_URL`). Components import the module of their area, so each lazily loaded screen carries its own strings.

**Layout.** Screens compose the primitives of `src/ui/layout.tsx` (`PageHeader`, `Section`, `Card`, `CardGrid`, `FormRow` and `FormAction`) instead of spacing boxes themselves: 24px between page sections, 16px inside and between cards, 12px between the controls of a form row, buttons on the line of the inputs whatever their hints. The navigation is a column from 768px up and a scrolling row on phones.

## Start from data

The Modeler's "Start from data" view (`?view=start`, `src/features/inference/`) turns tables you already have into a schema change, following `docs/inference.md`.

- **Source.** CSV or TSV files (drag and drop or a file picker; the file name is the table name) or a Postgres source reference. The caps (files, bytes per file, bytes in total, suffixes) come from the `VITE_INFER_*` variables and are checked before anything is sent; a file that breaks one is listed with the reason. A Postgres source is a secret reference that an administrator allowlisted on Keeper (`secret://env/ERP_DSN`): the field refuses anything else, so a connection string is never sent. The HTTP adapter posts multipart (`files`, `options`) for CSV and JSON (`postgres`) for the reference, both to `POST .../schema:infer`.
- **Review.** The proposal is read from the `yaml` of the answer and shown as a tree: Kinds with a confidence badge, the primary key evidence, and each Attribute with type, sample values, confidence and the reasons the engine gave; then the Relations with endpoints, cardinality, the inclusion ratio (read from the reasons of a reference) and evidence. Evidence is matched to elements by id, so renames keep it. Names are edited in place (a rename rewrites the references to it), types are changed from the list the schema editor uses (an enum is seeded from the sample values), elements are accepted or dropped one by one, and "Accept all at or above N%" accepts everything that reaches the threshold (default `VITE_INFER_ACCEPT_THRESHOLD`) except what was dropped. Accepting a Kind accepts its undecided Attributes. Only accepted elements are applied: a Relation needs both its Kinds and its reference Attribute, an Attribute that references a Kind that is not accepted is left out, and the screen says why. Primary key Attributes cannot be dropped. The inference issues (`infer.ambiguous_primary_key` and the others) are listed, with the count Keeper reports when it caps the list.
- **Apply.** The accepted elements are laid over the schema of the current Branch by api name: a new Kind or Relation is added as proposed; a Kind that exists keeps its key and settings and takes the proposed Attributes (an Attribute that exists keeps its id, so it becomes an update); a Relation that exists stays as it is. The schema rules of the editor run on the result, the dry run reports data migrations and violations, and the change set goes through the same panel as the editor: "Apply as schema change" commits on an unprotected Branch, and on a protected one it creates a Branch (`VITE_SCHEMA_BRANCH_PREFIX`), commits there and opens a Proposal. The YAML preview (read only, CodeMirror) always shows the accepted, edited proposal.
- **Limits.** Inference options (`options`) are not exposed in the UI, and Source mappings are not produced (the proposal is a schema, as in the inference document).

## Sources and Admin

- **Sources** (`/{domain}/sources`). The Sources of the schema on the current Branch with type, connection reference, mapping summary, sync mode and merge policy, schedule, last run and its counts; "Sync now"; the run history with the error of a failed run and a link to the Proposal a run opened; and the `sources` section of the schema as YAML, validated with the schema rules and saved as a change set. In live mode the HTTP adapter reads `GET .../sources/{source}/runs` (Keeper lists runs per Source, so the history merges the first page of each Source of the default branch) and "Sync now" calls `POST .../sources/{source}/sync`, which queues a job for Scribe. Keeper records no trigger, so that column shows `-`; reading runs needs a Domain-wide grant.
- **Admin** (Settings tabs, `?section=keys|access|audit`). API keys (create with name, role and lifetime, the secret shown once, revoke behind a confirmation), principals (filter by type) and grants (read only), and the audit log, newest first. Keeper's audit route only pages (`limit`, `cursor`), so the actor, action and text filters apply to the entries loaded so far and "Load older entries" fetches more. A members editor, chain verification and export are not built.

## Documents and extraction items

Following `docs/extraction.md` and design 9.2 and 12.3.

- **Documents** (`/{domain}/documents`, nav entry "Documents"). Drag and drop or pick files; the caps (documents per drop, bytes per document, suffixes) and the default tiers come from `VITE_DOCUMENTS_*` and are enforced before anything is sent. "Extract after storing" and the tiers (0 rules, 1 local models, 2 chat model) travel with the upload as `extract` and `tiers`. Each file is one request to `POST .../documents`, so one refusal (Keeper's 413 or 422, shown with its message) does not stop the rest; refused files stay in the list. A file Keeper already holds answers `duplicate` and queues nothing. A form takes a URL (and an optional file name) as the JSON body; Keeper fetches only hosts of `keeper.documents.url_hosts` and answers 422 otherwise, and `VITE_DOCUMENTS_URL_INTAKE=false` hides the form. The library lists documents newest first with their type, size, who added them, the status of the latest extraction job (queued, running, succeeded, failed with its error as the tooltip) and a link to the Proposal the job opened; it asks again every `VITE_DOCUMENTS_JOB_POLL_MS` while a job is on its way.
- **Document viewer** (`/{domain}/documents/{id}`). Metadata, the table of extraction jobs (status, model, prompt version, times, tokens, cost, Proposal) and the parsed text with the evidence of the Proposal's items highlighted: amber while pending, green accepted, struck through rejected, outlined for the selected item; overlapping quotes share one highlight. The URL carries `item`, `start` and `end`, so the item review links straight to its quote, and the list beside the text selects an item and links back to it in Review. The text comes from `GET .../documents/{id}/text` (`documents.text()`, `null` while it is not parsed; the viewer then shows the evidence passages, offsets and quote). Keeper cuts a long text at `keeper.documents.max_text_chars` and the viewer says so. Offsets count code points, so the viewer cuts the text by code point.
- **Items tab** (Review, a Proposal of origin `extraction`; `?tab=items&item=<id>`). All items of the Proposal are loaded (page after page, `VITE_EXTRACTION_ITEMS_PAGE_SIZE` each) and shown in one table grouped by type (new Records, Attribute values, Links) with the decision, what is proposed, a confidence bar (green from the threshold, amber a little below, red further below), the match (`matched`, `new`, `ambiguous`; a new Record that is not complete is flagged), the quote and a link to its place in the document. Filters: status, Kind or Relation, type, and a confidence range ("at least" is inclusive, "below" exclusive, as Keeper's `min_confidence` and `max_confidence`). They run on the loaded items with the same rules as Keeper's list filters.
- **Staging, then "Apply decisions".** Accept, reject and "back to pending" (buttons, or `a`, `r`, `u` on the selected row) only stage a decision, because Keeper checks the accepted set as a whole: a new Contract needs its `with_supplier` Link accepted in the same request. The bulk bar stages a decision for every item the filter shows, or accepts or rejects the pending ones above or below a threshold. "Apply decisions (N)" sends one `POST .../items:decide` with the staged decisions and edits and shows what Keeper made of them: items on the branch, changes, the Revision, and the accepted items it could not apply with the reason (`not_applied`, also shown on the item). A 422 shows its issues (and "Show item" selects the item they name), changes nothing and keeps the staged decisions. The bulk `where` of the route is part of the adapter (`decideItems({ where, decision })`); the screen expands filters to listed items because staged work and Keeper's one filter per request do not combine.
- **Selected item.** Evidence quote with the document and its offsets and a link into the viewer, the match, a candidate picker for an ambiguous match (choosing stages `key` for Records and values, `to` for Links), and inline edits: the Attribute values of a new Record, the value of a value item, `from`, `to` and Link Attribute values of a Link. Fields come from the schema of the target Branch (type, enum, constraints) and are checked before they are staged; only what differs from the item is sent as `edits`.
- **Schema suggestions tab** (Review, `?tab=suggestions`). Kinds, Attributes and Relations that document discovery proposes (`suggestions.list()`, `GET .../schema/suggestions`, paged with "Load more"). Filters: status (pending by default), type, and "Include below min support" (`all=true`). The table shows type, name, owner or ends (a Kind another suggestion proposes is `Name (new)`), support, documents, confidence, the type guess of an Attribute, status, and badges for duplicates and withheld evidence; a row opens its labels, samples and quotes with links to the document, and an optional name to accept it as. "Accept selected", "Reject selected" and "Reset" call `suggestions.decide()`; the accepted ones of one request become one change set on a new Branch and the screen links to the Proposal. A 422 (for example a Relation whose `+Kind` is not accepted in the same request) is shown with its findings and nothing changes.
- **Keyboard.** Like the Conflict resolver: arrow keys or `j` and `k` move between items, Home and End jump to the ends, `a`, `r` and `u` stage a decision.
- **Types.** `src/api/extraction-types.ts` aliases the generated wire types (`DocumentOut`, `ExtractionJobOut`, `DocumentUploaded`, `DocumentTextOut`, `MaterializedOut`, the item type and decision enums), with the members Keeper may leave out made explicit by the mappers. Items keep a view model of their own: evidence, match and edits are free-form objects on the wire.

## Conflict resolver

The merge attempt of a Proposal (design 6.8 to 6.10, 12.3) is the "Merge attempt" section of the Proposal detail, `src/features/review/`.

- **List.** Conflicts grouped by kind (`DV1` to `XS11`, with their names and counts), filters by kind, status (open, resolved) and text, a progress bar, and the Conflicts a policy already resolved. The selected Conflict is in the URL (`?conflict=<fingerprint>`), so a Conflict can be linked. The list is one listbox: arrow keys or `j` and `k` move between Conflicts, `Home` and `End` jump to the ends, "Next open Conflict" skips the resolved ones.
- **Resolver.** Base, ours and theirs side by side. Records are compared attribute by attribute and schema elements property by property (dotted paths, ids replaced by api names); only the paths where a side moved from the base are listed, with the rest one checkbox away. Absent sides (a deleted Record) are shown as absent. The choices are the ones the Conflict carries (`choices`, from `CHOICES` of its kind), never a fixed list.
- **Custom values.** The input follows the type: number field with the constraints of the Attribute, select for enums and booleans, date field, text area for long text, JSON text for Records, lists and schema documents. A value that breaks the type or the constraints, or JSON that does not parse, blocks "Save resolution" and says why. Types come from the schema of the source Branch.
- **Grouped Conflicts** (`XS1` to `XS9`) list their members with the values each side holds, take one value per member (`values` keyed by member key), offer "same value for every member", and accept the choices that need no value for the whole group.
- **Bulk.** One choice for every open Conflict of the current filter that accepts it; the button says how many it touches.
- **Apply resolutions** calls `POST .../merge`. Merged: the page shows the merged Revision (id, parents marked target and source, changes), the Resolutions applied and the policy resolutions. Conflicts remain: the list shows them, and a Resolution the merge run refused on re-validation is dropped and its reason appears on the Conflict.

Against Keeper (verified by `e2e/04-conflicts.spec.ts`): `GET .../conflicts` answers with the attempt and one page of Conflicts, `POST .../conflicts:resolve` stores Resolutions and answers with the re-run attempt, and `POST .../merge` answers 409 `merge-conflicts` with the attempt while Conflicts remain (the adapter turns that into `{ status: 'conflicts', attempt }`) and 409 `approvals-required` until the protected target has its approvals (Keeper does not take a merge into a protected Branch without them; the Proposal page has the review form for that). Keeper names a data partition `k:{kind id}` or `r:{relation id}` and an Attribute by id; the screens translate both with the schema of the source Branch (`partitionName`, `messageOf` in `conflict-meta.ts`). Values are in the canonical form of Keeper (design 6.1): integers and decimals are strings (`"80"`, `"24.01"`), and a custom value must be canonical too, so the number field produces `"55"` and pads decimals to the scale of the type (`canonicalNumber` in `src/api/values.ts`); a number is accepted in the sample data of the mock all the same.

## Schema editor

The Modeler's "Edit schema" view (`?view=edit`, `src/features/modeler/`) edits the schema of the current Branch as one document in two synchronized views.

- **Document.** The layout of `packages/core/src/lorebase_core/model/yaml_schema.py`: `format`, `domain`, then `kinds`, `relations`, `traits`, `operations`, `derivations` and `sources` keyed by api name, references by api name, `id` written always and honored on input (an explicit id keeps the element through a rename; without one the element with the same api name on the Branch is reused, else an id is minted). Types are written `string`, `decimal(12,2)`, `ref(Kind)`, `{enum: [...]}`, `{array: ...}`. Defaults are left out. `document.ts` converts between that layout and the id-keyed `Schema` of the API; built-in Operations are generated by Keeper and are not part of the document.
- **Form.** Kinds (name, status, primary key, title Attribute, Attributes with type, enum values, required, unique, indexed and constraints, Trait implementations with their mapping), Relations (endpoints, inverse name, cardinality, delete behavior, required, link Attributes), Traits (Attributes, implementing Kinds). Operations (parameters with types, preconditions, steps with their Kind or Relation and CEL values, review policy, permissions, side effects, rate limit, and a dry run of the saved Operation on the Branch), Derivations (`expression`, `aggregate` and `path` variants; the target Attribute is picked from the schema and declares the Derivation), Sources (type with the fields that type takes, a `secret://` connection, `http_json` headers, pagination, `since_param` and `max_pages`, key, Attribute and Relation mapping, scope filter, sync mode with watermark and tombstone columns, schedule, Branch template and merge policy). Renaming a Kind or an Attribute rewrites the references the document keeps to it, Derivations, Sources and Operation steps included. Expressions are edited in CodeMirror (`cel-field.tsx`), loaded with the first expression field. The forms of Operations, Derivations and Sources change only the keys they edit (`element-edits.ts`): any other key of the element stays as the YAML has it. Source transforms are edited per Attribute (`transform-editor.tsx`, the field set of each transform follows the core Source model), Operation steps are reordered by drag handle or keyboard buttons (`moveStep` renumbers `$step[n]`), a Source previews a sample file mapped onto its Kind in the browser (`source-preview.ts`, a port of the Scribe mapper that stays the reference) and a saved Derivation previews its computed Attribute on sample Records through the Record read.
- **YAML.** CodeMirror 6 with the YAML language, loaded on demand in its own chunk (shared with the expression fields) so the rest of the Modeler does not pay for it. `yaml` parses the text and writes it back. Typing valid YAML replaces the document; a form edit rewrites the text. While the text does not parse the form keeps the last valid document and is read only, and the syntax error is listed with its line.
- **Validation.** `src/api/schema-rules.ts` checks names, duplicates, references, types, constraints, cardinality, Trait mappings, Operation parameters, steps and empty expressions, Derivation targets and variants, and Sources as Keeper does (secret connections and credential headers, fields per type, watermark of incremental Sources, key mapping length, pagination options). Findings of Keeper's dry run, its CEL type check among them (`schema.expressions_enabled`), are shown under the field they are about too; the mock stands in for it with a syntax check and unknown `params.*` references (`src/api/mock/expressions.ts`). Every issue has a path in the layout of the document (`kinds/Supplier/attributes/tier/type`); it appears under the field it belongs to and in the issues list, where "Line N" moves the cursor of the YAML editor there. The same rules run in the mock before it accepts a change set.
- **Change set.** `diffSchemas` turns the edit into commands (`add_kind`, `update_attribute`, `remove_relation`, and so on, in `src/api/schema-changes.ts`); the summary lists them and shows the data migrations a dry run on the Branch reports (casts, defaults, dropped values). On an unprotected Branch "Save change set" commits a schema Revision. A protected Branch cannot take it: "Open Proposal" creates a Branch (prefix `VITE_SCHEMA_BRANCH_PREFIX`), commits the change set there and opens a Proposal against the protected Branch.

Keeper takes a change set as a document, not as commands: `POST .../branches/{b}/schema/changes` with the whole schema as `yaml` (and `dry_run`, `message`, `cascade`), `POST .../schema:validate` for a check that writes nothing. The live adapter therefore sends the document the editor holds (`SchemaChangeRequest.document`) and ignores `changes`; the commands drive the mock and the summary list. A change set Keeper refuses answers 422 with `issues`, which the adapter returns as `valid: false` with the findings (path as `kinds/Supplier/attributes/tier`), so the editor shows Keeper's own rules next to its local ones: an Attribute without a description, an id that is not a ULID, and so on. The Schema from Keeper is mapped to the view model and back to the same document without a difference (`src/api/live/schema.test.ts` checks it against a real schema and its YAML), and `e2e/03-schema.spec.ts` checks that an untouched schema produces an empty change set. Element ids minted by the editor are ULIDs with a first character 0 to 7, which is what Keeper accepts.

## Live mode

`VITE_API_MODE=live` makes the app talk to Keeper over `/api/v1`; `VITE_KEEPER_BASE_URL` says where. Two ways to reach it from a browser:

- **Same origin, through the dev proxy (recommended).** Set `VITE_KEEPER_BASE_URL=/` and start the app with `LOREBASE_KEEPER_PROXY=http://localhost:8080 pnpm dev` (or `pnpm preview`). The browser only talks to the app's origin, no CORS setup is needed, and the `ETag` header of Keeper is readable, so reads are conditional (below).
- **Cross origin.** Set `VITE_KEEPER_BASE_URL=http://localhost:8080` and let Keeper allow the app's origin: `keeper.cors.allow_origins: [http://localhost:5173]` and `keeper.cors.allow_headers` with `If-None-Match` added. Keeper does not expose `ETag` to cross-origin scripts, so conditional reads do not happen then (every read is a plain 200); everything else works.

To try it against the compose stack of `docs/quickstart.md`: start Postgres and Keeper, load a Domain with the `lorebase` CLI (the quickstart's steps 6 and 7), then

```bash
cd apps/web
printf 'VITE_API_MODE=live\nVITE_KEEPER_BASE_URL=/\n' > .env.local
LOREBASE_KEEPER_PROXY=http://localhost:8080 pnpm dev
```

### Authentication

Keeper in `keeper.auth.mode: none` (development) needs nothing. With `api_key` or `oidc`, set `VITE_API_TOKEN` or type the token into Settings, Connection: the adapter sends `Authorization: Bearer <token>` on every request. The token typed in Settings is kept in this browser's local storage and wins over `VITE_API_TOKEN`; "Forget stored token" removes it. **Both are development conveniences.** A `VITE_` variable is part of the bundle, and local storage is readable by any script on the origin, so neither belongs in a deployment that other people use; put the app behind a login or a proxy that adds the header instead. Settings, "Who am I", shows what Keeper (`GET /auth/whoami`) makes of the credential.

### Session mode

With `VITE_AUTH_MODE=session` (`authMode` in `/config.js`) the app does not handle a token. A person without a session lands on `/login`, "Sign in" sends the browser to Keeper (`GET /api/v1/auth/login?return_to=<path>`), Keeper runs the OIDC login and brings the browser back to the path it left. From then on the browser carries the session cookie; the app reads the session from `GET /api/v1/auth/session`, shows the display name in the top bar and sends the CSRF header (name and value from that answer) on every `POST`, `PATCH`, `PUT` and `DELETE`. If Keeper refuses a write with `reason: "csrf"`, the app reloads the session and repeats the request once. A `401` sends the browser to `/login`. "Sign out" calls `POST /api/v1/auth/logout` and then opens the end-session URL of the provider, or `/login` when Keeper returns none. A failed login comes back as `/login?error=<code>` with one of `login_expired`, `login_failed`, `access_denied`, `no_account` or `provider_unavailable`; the screen explains it.

Requirements:

- Keeper runs with `keeper.auth.sessions` enabled; without it `GET /auth/session` answers 404 and the app reports that sign-in is unavailable.
- Serve the app and Keeper on the same site, preferably on the same origin with `/api` proxied to Keeper (`VITE_KEEPER_BASE_URL=/`). The cookie is then first-party and needs no CORS.
- With Keeper on another origin, set `keeper.cors.allow_credentials: true` and list the app origin in `keeper.cors.allow_origins` (a wildcard is not accepted together with credentials) and, unless it is the origin of `app_url`, in `keeper.auth.sessions.allowed_origins`. See [deployment](../../docs/deployment.md#web-sign-in).

In this mode `VITE_API_TOKEN` is ignored and Settings, Connection, offers no token field.

### What the adapter does

- **Every method of `KeeperApi` has a route.** Domains, Branches (and tags), the schema (`GET`, `schema:validate`, change sets), Records, Links, query, traverse, neighborhood, search, the Branch log, Revisions, diff, Proposals with reviews, merge, Conflicts and Resolutions, Operation execution, `context`, `explain`, schema inference upload (`POST .../schema:infer`, multipart) and webhooks. Documents (`POST .../documents` as multipart with `file`, `extract` and `tiers` as JSON text, or as JSON with `url`; `GET .../documents`, `.../documents/{id}` and `.../documents/{id}/text`) and extraction items (`GET .../proposals/{p}/items` with one query parameter per filter value, `POST .../proposals/{p}/items:decide`).
- **Errors are problem details, typed.** `ApiError` has subclasses by code and status (`ProtectedBranchError`, `ApprovalsRequiredError`, `MergeConflictsError`, `ValidationError` with its `issues`, `NotFoundError`, `ForbiddenError`, `UnauthorizedError`, `ConflictError`, `UnavailableError`, `NetworkError` for no answer at all). The query client shows every failed read and write as a toast built by `describeError` (the problem detail, the first finding of a refused request, a hint to set the token on 401).
- **Conditional reads.** The fetch layer keeps the last answer per URL and credential and sends `If-None-Match`; a 304 serves the kept body. Keeper binds the `ETag` to the Revision, so an unchanged Branch costs no body.
- **Idempotent creates.** Creating a Domain, Branch or Proposal and merging a Proposal send an `Idempotency-Key` (a fresh UUID per call), and executing an Operation does too unless the request carries its own key. Keeper answers a create that carries a key with 200 and the existing resource when the name is taken by the same caller; since the keys are fresh, that is never a retry of ours, and the adapter reports it as `already-exists`.
- **Values.** Keeper writes integers and decimals as strings. The screens show them as they are, and the type-aware checks accept both forms.

### Limits against Keeper

- **Record history and lineage come from `explain`.** Keeper keeps no per-Record list of Revisions. History lists the writes `explain` knows (one per distinct write time, with the Attributes written then), and lineage lists the provenance of each Attribute. `explain` stamps every Attribute with the Revision that last touched the Record, so the adapter takes the creating Revision for the Attributes written at creation. Neither works at a past Revision (`at`): those answer 501.
- **Derived values** are not served by Keeper yet; a derived Attribute shows no value.
- **The built-in Operations** are not part of the schema Keeper serves (they are generated); the Operations list shows the stored ones.
- **Schema elements the editor does not model** are carried as they are when the document is written back (`status`, `watermark_column`, the `domain` block, descriptions of Trait Attributes); anything else a future schema version adds would not survive a save, which is why the round trip test compares against a real schema.
- **Previews of unsaved edits go through two read-only endpoints.** The Derivation preview reads a saved Derivation as Records and sends an edited one to `POST /derivations:preview`; the Source preview maps a sample file in the browser and sends only the sample rows (with the edited document) to `POST /sources:preview` when a mapping uses an `expression`. Keeper has no endpoint that reads the rows of a Source itself. The mock evaluates column references, literals and `+` only.

## Tests

`pnpm test` runs a router smoke test, one component test per screen (Start from data, Sources and Admin included, each against the mock: the wizard tests drive upload, edits, the threshold and apply; the Sources tests drive Sync now and the YAML editor; the Admin tests drive key creation, revocation and the audit filters), tests for the API adapters, the fetch layer, the typed errors and the config loader, and tests for the UI primitives. The Documents screen and the Items tab have component tests (upload and its caps, duplicates, options, URL intake, the job following its status, the viewer and its highlights; filters, bulk staging, apply with the materialized counts, the 422 of a Contract without its Link, the candidate picker, edits, the keyboard, a closed Proposal), unit tests for the item state and the span cutting, and tests of the mock's items and documents. The Conflict resolver has component tests for choice application, custom values and grouped values, and app-level tests for the merge attempt flow; the schema editor has tests for the form and YAML sync (the YAML view is driven through its CodeMirror state), validation, change sets and the protected Branch flow; the mock has tests for merge attempts, Resolutions and schema change sets. Component tests render the whole app against the mock adapter with an in-memory router history, so they exercise routing, URL state and data loading together. The live adapter has tests against a scripted Keeper (`src/api/http.test.ts`), and the schema mapper is checked against a real schema and its YAML (`src/api/live/fixtures/`, taken from a Keeper that loaded `examples/supply`). `src/api/generated/generated.test.ts` fails when the generated types are older than `docs/openapi.json`.

```bash
pnpm exec playwright install chromium   # once per machine
pnpm e2e                                # builds the stack, runs, removes it
LOREBASE_E2E_URL=http://127.0.0.1:8080 pnpm e2e -g "conflicts"   # one flow, Keeper already running
```

Reports and traces of a failed run are in `node_modules/.cache/e2e/`.
