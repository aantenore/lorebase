# Changelog

What changed in each release, newest first. The notes are written for the person deciding whether to upgrade; the rules are in [docs/launch/changelog-style.md](docs/launch/changelog-style.md). Lorebase follows semantic versioning. Before 1.0, any minor version may change an interface, and the notes say so.

## Unreleased

### Added

- An overlay for trying browser sign-in on the compose stack ([quickstart](docs/quickstart.md#26-open-the-web-app)): `deploy/compose/oidc-mock.yaml` starts a mock OpenID Connect provider in Keeper's network namespace, turns on `keeper.auth.sessions` and puts the web app in session mode (`WEB_AUTH_MODE=session`); set `LOREBASE_SESSION_KEY` in `.env`. The provider signs in anyone: local use only. One sign-in, session, CSRF-protected sign-out and expiry were checked through the `web` service ([validation](docs/validation.md)).
- `guide.http.default_origins`, the browser origins Guide accepts while `allowed_origins` is empty. The compose file sets it to the origins of its `web` service, so `GUIDE_ALLOWED_ORIGINS=[]` now behaves as unset (Guide logs a warning) instead of refusing the web app.
- A values schema for the Helm chart (`deploy/helm/lorebase/values.schema.json`): every value of `values.yaml` is typed, settings with a fixed set of values are enumerated, and unknown keys are refused except under `config` and `postgresql`, so `helm lint`, `template`, `install` and `upgrade` reject a misspelled key or a wrong type. CI lints and renders the `guide` profile and checks that the schema refuses bad values.
- Connectors: SQL Server `query` Sources can end in `ORDER BY` (Scribe appends `OFFSET 0 ROWS` inside the derived table), and `rowversion` watermarks are kept as hex in the run checkpoint and bound as bytes. `POST /domains/{d}/schema:infer` accepts named MySQL, MariaDB and SQL Server sources (`mysql`, `mssql`), read through a bounded sample under the same allowed-source rules and profiled like records (new `lorebase-keeper[mysql]` and `lorebase-keeper[mssql]` extras, `store.profiling.sql` settings). JSON uploads can hold their records under a key with the `records_path` form field (Python client `infer_files(records_path=...)`, web "Start from data"). The new `POST /domains/{d}/schema:preview` (`schema.write`, nothing stored; client `preview_files`) returns the first rows of uploaded files, and the web Source preview uses it for Parquet files.
- Explore in the web app ([guide](docs/guide.md#the-explore-panel-in-the-web-app)): a screen next to the Retrieval lab, and the same panel under the lab, that asks Guide a question about the Domain and shows each event of `POST /explore` as it streams in (reasoning notes, tool calls with compact arguments, result summaries and counts, errors, the answer and the totals). The request carries the caller's own credential (Bearer token, or the session cookie and CSRF header when Guide is served from the app's origin; `guideUrl` may be a path such as `/guide`). Stop aborts the request, a stream longer than `VITE_EXPLORE_TIMEOUT_MS` is stopped, and a 429 waits for `Retry-After`. Model output is rendered as plain text only; citations become links to Record pages when their Kind and key are valid, "View trace" opens the session in Agent activity, and the cited Records can be drawn on the Canvas. The `supply` Domain has five preset questions. Against the mock API the panel plays scripted explorations. New settings `VITE_EXPLORE_MAX_STEPS`, `VITE_EXPLORE_TIMEOUT_MS` and `VITE_EXPLORE_MOCK_STEP_MS`.
- Guide, an optional exploration assistant outside Keeper ([guide](docs/guide.md)). The new service `lorebase-guide` (package `lorebase_guide`) answers `POST /explore` with a stream of server-sent events: a small read-only agent reads the Domain through Keeper (schema, search, query DSL, Record, links, neighborhood, traversal, history, lineage and context packs), streams each tool call, a short result summary and the model's reasoning notes, and ends with an answer citing the Records it was shown, or "Not found in the graph." Every Keeper request carries the caller's own credential (Bearer token or API key, or the web session cookie with its CSRF token, checked against Keeper), so RBAC and masking apply exactly as for the user; Guide holds no credential and has no write tool. Each exploration is an agent trace session (`X-Lorebase-Session`, tool header, reasoning posted as notes). Budgets for steps, tokens per call, tokens per exploration and wall-clock time, per-credential rate and concurrency limits, and an Origin allow-list are in the new `guide` settings. `POST /embed` returns the vector of a query or document text with the configured embedding model and prefixes, the same vector Scribe stores for the same document text. Besides Scribe, Guide is the only package that may use `lorebase_inference`; the import contracts keep Keeper and Herald model-free and forbid them to import Guide. It runs from the backend image (compose profile `assistant`, Helm `guide.enabled`, off by default), and the web app reads its address from the runtime configuration `guideUrl` (`VITE_GUIDE_URL`).
- The Python client refuses empty, `.` and `..` path segments (Domain ids, Kind names, Record keys, relation names) and branch names with such parts, raising `ValueError` before any request: an HTTP client resolves them, which sent the request to another route.
- A quickstart that works from a fresh clone ([quickstart](docs/quickstart.md)). `make env` writes `.env` with generated database passwords, `make up` builds the image from the checkout and waits until Keeper is healthy, `make example-data` loads the `supply` sample and merges it into `main`, `make down` and `make clean-stack` stop the stack and delete its data. The quickstart adds an agent connected over MCP, a real model (Ollama in compose or on the host, or a hosted endpoint whose key is mounted from a file by `deploy/compose/hosted-model.yaml`), cleanup, a troubleshooting table and measured times. `.env.example` has `COMPOSE_PROJECT_NAME`, so two stacks on one machine no longer share containers and volumes, and Scribe and `inference-check` resolve `host.docker.internal` on Linux too.
- Ranked partial matching in lexical and hybrid search ([design 8.4](docs/design.md#84-search)). When `q` as written (every term) finds fewer than `search.partial.min_results` Records (1), Records holding some of its terms follow, after every full match: the words and quoted phrases of `q` joined by OR, negations kept for each, stop words of `search.partial.stop_words` (`english`) left out, scored `weight * (ts_rank_cd + term_bonus * terms held)` with typo corrections applied per term. Each hit reports `match` (`all` or `partial`, absent for hits found by vector only); the field is new and optional. Descriptive queries such as "ring that stops oil leaking" found nothing before, so hybrid search ranked them by the vector alone; the O-rings now come first lexically too ([validation](docs/validation.md#live-model-runs)). Measured at 100k Records in [performance](docs/performance.md#partial-matching-100k-records).
- Chat endpoint options for hosted providers ([inference providers](docs/inference-providers.md#anthropic)): `inference.llm.headers` sends extra HTTP headers (values accept `secret://` references, for example an `anthropic-workspace-id`), `extra_body` merges extra request fields (`reasoning_effort`, `thinking`, ...), `json_schema_strict` sets `response_format.json_schema.strict`, and `temperature: null` leaves the temperature out for models that refuse it. All four also work per task in `inference.llm.tasks`; a task on another `base_url` never inherits the headers. Header values are scrubbed from error text like the key. Anthropic's OpenAI-compatible endpoint and local Ollama models were run against the example documents; setup and results are in [validation](docs/validation.md#live-model-runs).
- Agent trace ([agent trace](docs/agent-trace.md), `keeper.trace`, off by default). Requests that opt in (`X-Lorebase-Trace: on`, or a listed principal or API key, or `trace_all`) become steps of the session they name (`X-Lorebase-Session`) or, without one, of an inferred session (same principal, credential and user agent, calls less than `inferred_session_idle_s` apart, marked `inferred`) in the new table `agent_trace_steps` (migration `0023`): tool (`X-Lorebase-Tool`), route, status, latency, response cache use, the query as structured data (filter values redacted unless `capture_literals`), result counts, search corrections, context pack budget and the Records and Links the answer touched, never values; with `X-Lorebase-Trace: debug` and the new permission `trace.explain`, query plan summaries. Agents attach notes with `POST /api/v1/trace/sessions/{id}/notes`; `GET /api/v1/trace/sessions` and `GET /api/v1/trace/sessions/{id}` list sessions and replay one. A principal sees its own sessions; the new permission `trace.read` (held by `admin`) shows other principals' steps in a Domain, with their query and note text only to readers holding every sensitivity clearance there (`withheld` otherwise). Steps are written off the request path in batches, capped per session and deleted after `retention_days` (7). Herald forwards the session id of the MCP client or session (none when there is none), the tool name and a `traceparent` on every Keeper call; the Python client takes `session_id`, `trace` and `tool` and has a `trace` resource; the CLI has `lorebase trace list|show`; the web app has an **Agent activity** screen with the timeline and the touched subgraph on the Canvas, step by step.
- Retrieval lab in the web app ([retrieval lab](docs/retrieval-lab.md)): one question, two parameter sets side by side (mode, weights, thresholds, limits), lexical results with scores and corrections, semantic and hybrid ones when a query vector is pasted or an embedding service is configured (`guideUrl` in the web app's runtime configuration; the browser calls it, never Keeper), the context pack an agent would get with why each entry is in it and its tokens against the budget, and the involved Records on the Canvas. `POST /search` takes `tuning` (`lexical_weight`, `semantic_weight`, `rrf_k`, `trigram_weight`, and the work bounds `typo_candidates` and `candidates`, which may only be lowered, and `trigram_threshold`, which may only be raised) in place of the `search` settings for one request.
- Schema suggestions from document extraction ([extraction](docs/extraction.md#schema-suggestions)). Extraction jobs report what they see outside the schema: `**Label:** value` fields and table columns no Attribute matches, headings naming a thing by a code no Kind knows, spans and relations of the new `scribe.extraction.discovery.span_labels` and `relation_labels`, and, at tier 2, an `unlisted` list in the answer schema plus records, values and links outside the schema, all with verified evidence. Observations are matched against the schema (normalized singular names, synonyms, similarity), never kept when they match a sensitive Attribute, kept without evidence when the quote holds a sensitive value, and aggregated per Domain by fingerprint into suggestions with support, documents, examples, samples and, for Attributes, the type schema inference gives the samples; extracting a document again does not count it twice. `GET /api/v1/domains/{domain}/schema/suggestions` lists them (permission `document.read`; pending ones from `schema.suggestions.min_support`, at most `max_suggestions`) and `POST .../schema/suggestions:decide` rejects, resets or accepts them: accepted suggestions become one schema change set on a new branch (`keeper.schema_suggestions.branch_prefix`) proposed into the default branch, new Kinds and Relations as drafts. The web app has a Schema suggestions tab in Review and the Python client `schema.suggestions`, `iterate_suggestions` and `decide_suggestions`. New settings `schema.suggestions`, `scribe.extraction.discovery` and `keeper.schema_suggestions`; migration `0021` adds the `schema_suggestions` table. The tier 2 cache key changes when discovery is on, so the first run after upgrading calls the model again.
- `lorebase schema import --from linkml --apply` merges into the current schema of the Domain instead of replacing it: Operations, Derivations, Sources and the fields LinkML cannot carry (`derivation`, `authority`, `indexed`, ...) are kept, elements match by id or name, and Kinds, Attributes, Relations and Traits missing from the LinkML file are kept with a warning unless the new `--prune` flag removes them; `--dry-run` shows the resulting change set ([LinkML](docs/linkml.md#import)).
- LinkML schema import and export ([LinkML](docs/linkml.md)). `lorebase schema export --format linkml` translates the schema of a Domain, or a local document with `--file`, into a LinkML schema: Kinds become classes, Traits mixin classes, Attributes class attributes with their range, `required`, `identifier`, constraints and `ifabsent`, enums LinkML enums, and each Relation a pair of slots linked by `inverse` whose `multivalued` gives the cardinality. Element ids, sensitivity tags, search settings and the types LinkML lacks travel as `lorebase.*` annotations, Operations, Derivations and Sources as schema annotations, so importing the export gives back the same schema. `lorebase schema import FILE --from linkml` prints the Lorebase document (or writes it with `-o`), `--apply` and `--dry-run` send it to a branch like `schema apply`; what it leaves out (Operations, Derivations and Sources, `is_a` inheritance, which it flattens, abstract and `tree_root` classes, inlined objects, rules, `any_of`, enum meanings, custom type constraints) is reported as warnings with their path, and classes without slot descriptions or a title attribute are imported as `draft` Kinds. The translation needs PyYAML, in the new optional extra `lorebase-cli[linkml]`.
- Path Derivations work ([design 5.8](docs/design.md#58-derivation)). A `path` Derivation is a virtual Relation (`A -r1-> B -r2-> C` read as `A -> C`) usable by its `api_name` or `inverse_api_name` wherever a Relation name is accepted from a Kind: Links of a Record and of a Relation, `via` and `count` predicates, `include` and traversal. By default its Links are composed at read time from the steps' Links (overlays and row-level security included); every later step follows at most `store.traverse.path_fanout` Links (100) per intermediate Record, smallest far keys first. With `materialized: true` the Links are stored in `mat_links` under the Derivation id and kept current in the commit transaction: only the start Records a changeset can affect are recomputed (above `store.materialize.derivation_max_incremental_records`, the whole path), schema changes and rebuilds rewrite them, and `verify(..., derived=True)` checks them. Both modes give the same Links, also at past Revisions, where they are composed from the tree. Following a path needs read access to every Kind it crosses. Path Links carry no values.
- Trait queries at a past Revision (`at`): `POST /query` with `trait` lists the Records of every implementing Kind from the tree, in the head's order and with the head's cursors; filters, ordering by other fields, includes and aggregates stay refused there (422 `time_travel`), as for Kinds.
- MySQL/MariaDB and SQL Server Sources: the types `mysql_table`, `mysql_query`, `mssql_table` and `mssql_query` read a table or a query like the Postgres ones (snapshot or incremental with a watermark compared in SQL, batches of `fetch_rows`, connection by allowed `secret://` reference, `statement_timeout_ms` and `connect_timeout_s` in the new `scribe.sources.mysql` and `scribe.sources.mssql` settings) and can be profiled for schema inference. The drivers are optional extras and a run without one fails naming it: `lorebase-scribe[mysql]` (asyncmy; the session is read-only) and `lorebase-scribe[mssql]` (pymssql in worker threads, no ODBC driver to install; use a login that can only read, since SQL Server has no read-only transaction). Schema validation asks the new query types for a query, and the web Modeler lists the types and keeps them on a round trip ([scribe](docs/scribe.md#sources)).
- Operation side effects ([design 10.5](docs/design.md#105-side-effects), [agents](docs/agents.md#operation-events)). A stored Operation's `side_effects` (unique snake_case names of at most 64 characters, now checked by schema validation as `schema.api_name_invalid` or `schema.api_name_duplicate`) make each committed execution write one `operation.<name>` outbox event in the transaction of its Revision, invocation record and audit entry, so the event exists exactly when the execution committed; dry runs, refusals, executions that need review (agent `task` writes that open a Proposal included) and idempotent replays write none. The payload names the execution, carries the parameters as recorded (possibly sensitive ones `***`) and up to `keeper.operations.side_effect_max_edits` (100) edits. Webhooks subscribe with `operation.<name>` or `operation.*`; a webhook created without `events` now gets `revision.committed` and `operation.*`. Sensitive values in events reach a webhook only when it was created with matching `clearances` (`pii`, `confidential`, `restricted`; creating one needs that clearance permission on the Domain), others get `webhooks.masked_value`; vault values are stored as references and opened when the delivery is sent, so an erased one arrives as `webhooks.erased_value`. Every attempt of an event carries `Idempotency-Key: evt_<sequence>` (`webhooks.idempotency_header`): delivery is at least once and unordered. Each consumer of the outbox now keeps its own delivery state (`outbox_pending`, filled by a trigger in the writing transaction), so a second consumer no longer loses events to the webhook worker, and an event whose transaction commits late is not skipped. Outbox events are pruned once every consumer handed them off and they are older than the new `store.outbox.retention_s` (7 days; `webhooks.retention_s` now applies to deliveries only), or after `store.outbox.max_age_s` (30 days) in any case, `store.outbox.prune_batch` (10,000) at a time. New metrics `lorebase.outbox.handoffs`, `lorebase.outbox.pruned` and `lorebase.operations.events`. Migration `0020` adds `outbox_consumers`, `outbox_pending` and `webhooks.clearances`, moves undelivered events to the `webhooks` backlog and drops `outbox.delivered_at` and `outbox.attempts`.
- Rate limits shared by every Keeper: `keeper.limits.rate.backend: postgres` keeps the token buckets in the application database (the UNLOGGED table `rate_limit_buckets`), so several Keepers enforce one limit instead of each its own. A Keeper leases a few tokens per query (`postgres.lease_tokens`, at most a quarter of a bucket) and serves requests from them, so most requests cost no query and the Keepers together never exceed a limit. Failed-authentication buckets are written on every failure and fail closed (429) when the database does not answer within `postgres.timeout_s`; the other buckets follow `postgres.on_error` (`local`, the default, enforces them in the process meanwhile; `allow`; `deny`). The default backend is now called `local` (`memory` still works). The Helm chart sets `postgres` when `keeper.replicaCount` is above 1 or the HPA is on (`keeper.rateLimitBackend` overrides it); compose reads `KEEPER_RATE_LIMIT_BACKEND`, to set with the `scale-out` profile. New metric `lorebase.ratelimit.shared.queries` ([operations](docs/operations.md#rate-limits-and-quotas)).
- Auditing of reads (`keeper.auth.audit.reads`, off by default). Successful reads of authenticated callers are recorded in `audit_read_log`, a table with hash chains of its own (per Domain and installation-wide) so that sampled, droppable read records never touch the chains of actions. `sample_rate`, `principal_types` and `kinds` choose which reads are kept, except that a read that showed or masked a sensitive value (`pii`, `confidential`, `restricted`, vault values included) is always recorded, with `sensitive: [shown|masked]`. Records are queued and written in batches off the request path; a full queue or a failed batch drops records, counted in `lorebase.audit.reads.dropped`. `python -m lorebase_keeper audit verify --reads` verifies the read stream and the daily `audit_verify` job checks both streams ([operations](docs/operations.md#read-auditing)).
- Signed checkpoints of the audit chains outside the database (`scribe.audit_checkpoints`, off by default). An `audit_checkpoint` job, every `interval_s` (one hour), signs the newest entry of every chain with an Ed25519 key and stores it in a directory (never replacing a file), at an HTTP endpoint or in an S3-compatible bucket (PUT signed with Signature Version 4), with the address checks and pinning of webhook targets. `python -m lorebase_keeper audit verify --checkpoints PATH --checkpoint-key PUB` reports checkpointed entries that are missing or changed, so a table owner who cuts the end of a chain or recomputes one is detected. New metric `lorebase.audit.checkpoints` ([operations](docs/operations.md#checkpoints-outside-the-database)).
- The five-day proof scenario runs in CI. The End-to-end workflow builds the backend image from the checkout (Docker layers cached), starts the demo stack with the deterministic fake inference provider and runs `examples/five_day_demo/run.sh` on pushes to `main`, nightly, on demand and on pull requests that change `examples/`, `packages/`, `deploy/compose/` or `deploy/docker/`; on failure it uploads the stack logs and the run transcript. Every day of the demo now ends with assertions (`demo.py assert-*`: schema applied, import counts, merge with resolved Conflicts, Source runs and webhook, agent writes through Proposals and the audit log, restore equals live), a failed one exits non-zero, and the run prints the seconds each day took. Day 2 gained a document: a contract extracted with the deterministic tiers into a Proposal of items that is reviewed and merged, and the agent of day 5 now also opens a Proposal of its own with `task` and `intent` (its key gets the `editor` role on `agent/*`). `DEMO_NO_BUILD=1` makes `stack.sh up` use a prebuilt image ([demo](docs/demo.md#assertions-and-ci)).
- Personal data vault and erasure ([design 13.5](docs/design.md#135-personal-data-and-erasure)). An Attribute tagged `pii` with `vault: true` stores its values encrypted (AES-256-GCM) in the `vault` table, and Record objects hold a token `{"$vault": "vlt_..."}` instead; hashes, diffs and merges compare tokens, which stay the same for the same value of the same Attribute of the same Record. `POST /api/v1/domains/{domain}/vault/erase` (new permission `pii.erase`, `admin` only among the built-in roles), `lorebase admin erase KIND --key K` or `--attribute A --value V`, and `vault.erase_record` / `erase_value` in the Python client erase a data subject's values on every branch and Revision, in one transaction with an audit entry that never holds the value; erasing again changes nothing, and reads show `keeper.reads.sensitivity.erased_value` (`[erased]`). Keys come from the new `vault` settings (`token_key`, `encryption_key`, `key_id`, `previous_keys`), the same for every process that commits; without them, writes of vault values are refused (`value.vault_unavailable`). Vault Attributes cannot be unique, indexed, derived, references, titles, primary keys or foreign keys, and vault storage cannot be turned on or off on an existing Attribute (`schema.vault_invalid`). References are accepted in writes only for the Record they belong to, and Conflicts over vault values are resolved by picking a side. Bundles carry tokens, never vault values, and their import refuses plain values in vault Attributes. `lorebase admin erase --value -` reads the value from standard input. Migration `0019` adds the columns that bind a vault row to its Record. The Modeler keeps `vault` when it edits a Kind.
- Sensitivity masking on reads ([design 10.2](docs/design.md#102-rbac)). Values of Attributes tagged `pii`, `confidential` or `restricted` are shown only to callers holding the new permissions `pii.read`, `confidential.read` or `restricted.read` (Domain-wide, on the branch read, or narrowed to the Kind; `admin` holds them, custom roles grant them); other callers get `keeper.reads.sensitivity.masked_value` (`***`), or nothing with `omit: true`. This covers Records, Links, query includes, traversals, neighborhoods, history and lineage values, diffs and changesets, explain and context packs, Conflicts and stored resolutions, and Operation edits, so the CLI, the Python client and the MCP server see the same. Filtering, ordering or grouping by a sensitive Attribute needs the clearance (403 `sensitive_attribute`), and by a vault Attribute is refused (422 `vault_attribute`). Responses are cached and tagged per clearance. Clearances come from Domain-wide grants or grants narrowed to the Kind (by its id on the default branch), not from grants narrowed to a branch; the tags of the default branch, carried through Derivations, apply to every Revision and branch read; removing a tag on any branch, by a schema change or a merge, needs its clearance (403 `sensitivity_lowered`), and writers without a clearance check (agent auto-merge, Source merges) cannot. Derived Attributes and the step values of Operations must carry the tags of what they read, preconditions cannot read sensitive Attributes (`schema.sensitivity_inherited`), sensitive Attributes cannot be primary or foreign keys, and uniqueness violations on them no longer name the other Record. Extraction items are masked too, Operation invocation records and Proposal descriptions no longer keep parameter values that may be sensitive, and Source run errors are shown only to callers cleared for every tag of the schema.
- Copies and deletions of large branches run in the background, so they no longer hit `database.statement_timeout_ms` (at 1M Records a copy took 85 to 95 s and failed through the API). A copy branch whose source holds more than `store.materialize.async_copy_min_rows` Records and Links (10,000) is created at once as an overlay of its source, readable and writable right away, and a `store.materialize` job copies its rows in batches of `job_batch_rows`, one transaction each, resuming from its cursor after a failure, then switches the branch to a full copy. Commits on the branch and on its source stay correct during the copy and wait for at most one batch; a schema change on the branch is refused with 409 `branch-materializing` and `Retry-After` until it is done. Deleting a branch with more than `async_delete_min_rows` rows hides it at once and a `store.branch_delete` job deletes its rows in batches. At most `job_concurrency` of these jobs run at once across workers. Branch responses have `materialization_status` (`pending`, `running`, `done`, `failed`) and `materialization_progress`; `lorebase branch create --mode copy --wait` waits for the copy, and `lorebase branch list|get` show it. Overlays promoted because their base moved too far are copied the same way. New metrics `lorebase.store.branch_jobs.rows`, `.runs` and `.batch.duration`. Migration `0017` adds `refs.deleted_at` and the `branch_materializations` table ([operations](docs/operations.md#large-branches), [store schema notes](docs/store-schema-notes.md#large-branches)).
- The embedding model of a Domain is advertised to agents: `GET /api/v1/domains/{domain}/schema` has a `search` block with the search `modes` and, when a Kind has `search.embedding_template`, `embedding` (`model`, `dims`) read from `search.semantic.model` and `store.embeddings.dims`; `lorebase_schema` shows it as a `SEARCH` line, and the Python client has `SchemaDocument.search`.
- `inference.embeddings.query_prefix` and `document_prefix` (empty by default) for models trained with prefixes, such as E5: `lorebase-inference embed --query TEXT` puts the query prefix before the text, and Scribe puts the document prefix before every embedded Record text. Changing the document prefix makes the next pass embed every text again. `lorebase-inference embed TEXT` without `--query` no longer adds anything, which is what it did before prefixes existed ([inference providers](docs/inference-providers.md#embeddings-for-search)).
- Garbage collection deletes the embeddings no branch head references (for example the vectors of Records that only a deleted branch held); `python -m lorebase_store.gc --dry-run` and the `gc` job report their count as `embeddings` ([operations](docs/operations.md#garbage-collection)).
- The Modeler edits `search.embedding_template` and `search.embedding_sensitive` on the Kind form, checks the placeholders against the Kind's Attributes (unknown, derived and sensitive ones) before a change is sent, and follows an Attribute rename in the template.
- Embedding jobs for semantic and hybrid search. A Kind opts in with `search.embedding_template` in the schema (`{attribute}` placeholders by api name, plus `{_kind}` and `{_key}`; sensitive Attributes only with `search.embedding_sensitive: true`; invalid templates are reported as `schema.embedding_template_invalid`). Scribe's scheduler queues an `embeddings` job per Domain every `scribe.scheduler.embeddings_interval_s` (60 s): it embeds, branch by branch, the Records that lack a vector of the configured `inference.embeddings` model, re-renders the Kinds whose template changed, skips texts whose hash did not change and copies the vector of an identical text instead of calling the model. Vectors stay keyed by content hash, so overlay and copied branches only add work for the Records they change. Batching, a row budget per job with resumable continuations, call pacing and retries come from the new `scribe.embeddings` settings; the model's dimension is checked against `store.embeddings.dims` before the first call. `lorebase-scribe embeddings DOMAIN [--branch B] [--reindex] [--prune]` backfills, reindexes and, after a model switch, deletes the vectors of other models. New metrics `lorebase.scribe.embeddings.records` and `lorebase.scribe.embeddings.call.duration`. Migration `0014` adds `embeddings.text_hash` and the `embedding_cursors` table ([scribe](docs/scribe.md#embeddings)).
- Query vectors on the caller's side, since Keeper and Herald never call a model: `lorebase-inference embed TEXT` prints the vector of the configured embedding model, and `lorebase search TEXT --vector-file FILE` (`-` for standard input) sends it for hybrid search ([inference providers](docs/inference-providers.md#embeddings-for-search)).
- Per-Record history and lineage: `GET /api/v1/domains/{domain}/kinds/{kind}/records/{key}/history` lists the Revisions that changed a Record on a branch, newest first, with the changed Attributes, their provenance and, with `values=true`, the values before and after; `GET .../records/{key}/lineage` tells per Attribute where the current value came from (provenance, Revision, Source, Operation, extraction evidence, Proposal). Both read one index range of the branch history, are authorized and cached like Record reads, and are bounded by the new `read.history` settings. Also in the Python client (`records.history`, `records.lineage`), the CLI (`lorebase record history|lineage`), the MCP server (`lorebase_history`, `lorebase_lineage`) and the History tab of the Explorer Record page.
- Merge policies `authority` and `newest_wins` ([design 6.10](docs/design.md#610-resolution-flows)). `authority` (globally or per Attribute in `authority_attributes`) is a ranked list of origins such as `source:<id>`, `principal:<id>`, `actor:<id>` or `origin:extraction`: on an attribute value Conflict the side whose last change comes from the higher ranked origin wins, and `schema_authority: true` ranks an Attribute's schema `authority` Source first. `newest_wins` (or `newest_wins_attributes`) takes the side whose last change has the later provenance time, equal times going to the greater provenance id. Both read the Lineage of both branches, leave the Conflict to a person when they cannot decide, and record why they decided in the attempt's `auto_resolutions[].details`, which the Review screen shows. Set them in the Domain's `merge_policy` setting; Source merges apply them too.
- Sign-in for the web app with Keeper as backend-for-frontend (`keeper.auth.sessions`, off by default; needs an `oidc` auth mode). `GET /api/v1/auth/login` runs the OpenID Connect authorization code flow with PKCE against the configured provider, `GET /auth/callback` checks state, nonce and the ID token and sets an opaque `HttpOnly`, `SameSite=Lax` session cookie (`__Host-` prefixed and `Secure` unless `cookie_secure: false`), `GET /auth/session` returns the user and the session's CSRF token, and `POST /auth/logout` ends the session and returns the provider's end-session URL. Sessions live in the new `web_sessions` table (migration `0013`; only a SHA-256 of the session id is stored, provider tokens are encrypted with `sessions.encryption_key`) with idle and absolute timeouts, a new id on every sign-in and refresh-token checks at the provider. A session maps to the same principal, groups and grants as the user's bearer tokens; POST, PUT, PATCH and DELETE with the cookie need the CSRF header, a trusted `Origin` and no cross-site `Sec-Fetch-Site`. API keys, bearer tokens and `auth.mode: none` work as before. The web app gets `VITE_AUTH_MODE=session` (`authMode` in `/config.js`): a sign-in screen at `/login`, a sign-out button, cookie requests with the CSRF header, and a redirect to sign-in on 401 ([deployment](docs/deployment.md#web-sign-in)).
- Operation, Derivation and Source editors in the web app Modeler ([tour](docs/tour.md#edit-schema)). Operations: typed parameters, preconditions, steps with their Kind or Relation and values, review policy, permissions, side effects, rate limit, and a dry run of the saved Operation on the Branch. Derivations: `expression`, `aggregate` and `path` variants, with the computed Attribute picked from the schema. Sources: the fields of each type (`records_path`, `flatten_separator`, `http` headers and pagination for `http_json`), `secret://` references only for connections and credential headers, key, Attribute and Relation mapping, sync mode with watermark, schedule and merge policy. Expressions are edited in a CEL editor, and the findings of Keeper's dry run, the CEL type check included when `schema.expressions_enabled` is on, appear next to the field. Edits go through the same change set, Branch and Proposal flow as the other editors, and keys a form does not edit stay as the YAML has them.
- Helm chart values for the web sign-in: `config.keeper.auth.sessions` settings, the OIDC client secret and the session encryption key read from the Secret (`secrets.keys.oidcClientSecret`, `secrets.keys.sessionEncryptionKey`, or `secrets.values.*` for a chart-managed one) and wired as `secret://env` references, `web.config.authMode: session`, render-time checks, and the `ci/sessions-values.yaml` overlay ([Kubernetes](docs/kubernetes.md#web-sign-in)).
- Audit chain verification ([operations](docs/operations.md#audit-chain-verification)). `python -m lorebase_keeper audit verify DOMAIN|--installation|--all` recomputes the hash chains of the audit log with the maintenance DSN, prints the first entry that does not verify (or JSON with `--json`) and exits 1 when there is one; `--after-seq` resumes from the `last_seq` of an earlier run. `GET /api/v1/domains/{domain}/audit/verify` (permission `audit.read`) and `lorebase audit verify` (exit code 2 on a broken chain) check one Domain's chain, and the Python client has `audit.verify`. Entries are read in batches, so memory does not grow with the log. Scribe queues an `audit_verify` job of every chain each `scribe.scheduler.audit_verify_interval_s` (one day; 0 disables it), counted in the new metric `lorebase.audit.verifications` by outcome, and the `LorebaseAuditChainBroken` alert fires when a chain is broken.
- A [threat model](docs/threat-model.md): STRIDE per trust boundary (web sign-in, API keys and OIDC, authorization in Keeper, Scribe connectors and document intake, Herald, Postgres roles and row-level security, webhooks, inference providers, the release pipeline), each mitigation with the file that implements it, and the residual risks in order of priority.
- An [API stability policy](docs/api-stability.md) for `/api/v1`: what is stable, which changes are compatible or breaking, the deprecation process with `Deprecation` and `Sunset` headers (none is deprecated yet, so Keeper sends neither), client compatibility, MCP tool stability and the `lorebase.schema/v1` format. It binds from 1.0; before it, breaking changes are named in the changelog.

### Fixed

- Embedding vectors are keyed by the fingerprint of the embedding template as well as by content hash and model (migration `0024`). Branches whose templates differ for the same content keep a vector each instead of overwriting one another, and Keeper's semantic and hybrid search read the vectors of the searched branch's template. Vectors of identical texts are still copied without a model call, now across templates too. The upgrade sets the fingerprint wherever every branch holding the content agrees on one template, and the next pass re-renders each text once to fill in the rest. Garbage collection also deletes vectors of templates no branch uses any more. Scribe resolves embedding templates once per schema hash and keeps the last `scribe.embeddings.template_cache_size` schemas.
- `LorebaseGcNotRun` no longer fires for a gc schedule set to dry runs (`scribe.scheduler.gc_dry_run: true`). Scribe counts the collections it schedules in `lorebase_gc_scheduled_total{dry_run}`, and the alert needs real scheduled collections (`dry_run="false"`) that never complete within 3 days. The Scribe dashboard shows scheduled runs next to completed ones.
- `lorebase_jobs_queue_depth` reports jobs waiting for a retry delay (queued with a `run_after` still ahead) as `status="retrying"`, so `queued` counts only claimable jobs and `LorebaseJobQueueStalled` no longer counts jobs no worker could claim yet.
- LinkML: path Derivations are exported as slots carrying their steps, inverse name and `materialized` as annotations, and `schema import --apply` reads them back, so a round trip keeps them. Applying to a Domain no longer warns that Operations, Derivations and Sources are not imported when the merge keeps them, and `--prune` without `--apply` or `--dry-run` is refused instead of doing nothing.
- Schema suggestions no longer list one fact twice under two names: Attribute suggestions of the same Kind whose names share at least `schema.suggestions.merge_similarity` of their words (0.6) and whose samples share a value type are folded into the better supported one (`renewal_notice_days` and `renewal_proposal_notice_days`, `termination_notice_days` and `termination_for_cause_notice_days`). Kinds named by a generic document or workflow word (`schema.suggestions.kind_stoplist`) or by an Attribute (`Buyer` beside `buyer`) are not suggested, and a proposed Kind is listed once it has `kind_min_attributes` (2) Attribute suggestions or as many observations.
- Tier 2 extraction asks for link Attributes: a Relation with link Attributes has its own branch in the answer schema with the link's `values` (evidence for each, the required ones required), and the prompt asks for the required ones. Link values are verified and grounded like record values and reach the Link item; before, `stocked_at` Links came without `quantity`. A Link item still missing a required link Attribute stays pending, with the names in `match.missing`.
- A structured output mode an endpoint refuses is remembered for the process, per `base_url`, model and output settings, instead of being tried again at the start of every extraction job (two refused requests per job with a strict-only endpoint before).
- A tier 2 chunk whose answer stays invalid after the repair attempts no longer fails the whole extraction job: the chunk is skipped with a warning, counted as `model_invalid_answers`, and its tokens still count toward the job budget and usage. An answer cut off before any output says that a reasoning model may have spent the token limit on reasoning.
- Tier 2 timestamp values written without an offset (`2024-01-23`, `2024-01-23T10:15`) are read as UTC instead of being discarded as invalid, and timestamps are grounded by their day in the quote ("approved on 23 January 2024").
- A webhook receiver that disappears no longer holds a Scribe worker. Each delivery attempt, host lookup and every checked address included, is now cut off after `webhooks.timeout_s`; before, the budget applied to each address in turn, the lookup had none, and one pass sent up to `webhooks.batch` deliveries one after the other, so a receiver that accepted connections and never answered, or dropped packets, kept a `webhook_delivery` job running for many minutes while its heartbeat kept it from being requeued. Connections give up after the new `webhooks.connect_timeout_s` (5 s) and try the next checked address; a pass sends `webhooks.concurrency` (8) deliveries at a time, starts none after `webhooks.pass_timeout_s` (60 s) and releases the rest to the next pass without counting an attempt; a pass still running after `webhooks.lease_s` fails its job attempt. `webhooks.lease_s` must now exceed `pass_timeout_s + timeout_s` (the defaults do). Timed-out attempts are retried with backoff and marked dead after `max_attempts` as before, and counted in the new metric `lorebase.webhooks.timeouts` ([operations](docs/operations.md#lorebasewebhookdeliveryfailing)).
- The compose `db-roles` step grants the application role EXECUTE on all eight security definer read functions of a database migrated before the role existed (it granted only the four of revision 0005), reading them from the catalog like the Helm chart's role setup does.
- Guide no longer overshoots its token budget by up to the steps times `max_result_chars`: before each model call it estimates the input (prompt, messages and tool results so far) and calls only when used plus estimated input fits in `guide.agent.max_total_tokens`, with the completion cap cut to what remains after the estimate. The `session` event now names the chat `model` and the effective `max_steps` of the run ([guide](docs/guide.md)).
- Outbox pruning keeps up with high event rates: a pass deletes batches of `store.outbox.prune_batch` events, each in its own transaction, until nothing is left or the new `store.outbox.prune_budget_s` (5 s) is spent, instead of one batch per pass. The new gauge `lorebase.outbox.prune.backlog` reports the events still prunable after a pass (counted up to 100,000) and the alert `LorebaseOutboxPruneBacklog` fires when it stays above 50,000 for 30 minutes ([operations](docs/operations.md)).

### Changed

- mypy no longer carries a project-wide override for `pyarrow` (reported as an unused section when only some packages are checked): the three optional pyarrow imports ignore its missing type information where they are.
- Kubernetes, in-cluster database: one `helm upgrade` now adds the application role ([kubernetes](docs/kubernetes.md#database-roles)). A `pg-roles` pre-upgrade hook Job declares the roles of `postgresql.cluster.roles` on the CloudNativePG Cluster and waits for the operator before the migration Job runs; upgrading a release that used one DSN no longer takes two upgrades. It needs access to the API server when egress is restricted (`networkPolicy.egress.kubernetesApi`); `database.setup.clusterRoles.enabled: false` turns it off.
- Sensitive Attributes are left out of full-text search for every caller: their words are no longer in search vectors, the lexicon, corrections or snippets (a `searchable` sensitive Attribute gets the warning `schema.sensitive_attribute`), and a Kind whose title Attribute is sensitive has Records without a title. Semantic and hybrid search use the vectors of a Kind that embeds sensitive Attributes only for callers cleared to read them. Rows materialized before keep their titles and search vectors until the Kind's definition changes on that branch (any edit of the Kind, such as its description, recomputes them); `materialize.verify` reports such rows until then.
- Validation messages of schema migrations no longer quote values of sensitive Attributes.
- Deleting a branch above `store.materialize.async_delete_min_rows` rows returns 204 at once while its rows are deleted in the background; until then its name stays taken, and creating a branch with it answers 409 `already-exists` with `Retry-After`. Copies above `async_copy_min_rows` answer with `materialization: overlay` until their copy is done. Set both thresholds very high to keep copies and deletions in the request transaction.
- Typo-tolerant search matches words instead of whole titles. Each branch keeps, per Kind, the distinct words of its search vectors (`mat_lexicon`, kept by triggers on `mat_records` in the writing transaction; an overlay adds its base's), and a query word the searched Kinds do not hold is corrected to their closest words by trigram similarity (negated words are left alone), then searched as `(word | correction ...)`. Hits of the query as written rank first, the others after them at `search.trigram_weight` times their rank. `POST /search` responses have `corrections` (`word`, `replacements`; empty when nothing was corrected), also in the Python client (`SearchResult.corrections`) and in `lorebase_search`. `search.trigram_threshold` is now the least similarity of a correction (default unchanged, 0.3), and `search.typo_candidates` (3; 0 turns it off) and `search.typo_min_length` (4) are new. Words are lexemes of the text search configuration, so a stemming configuration reports stems. Migration `0018` adds the table, its triggers and backfill (writes to `mat_records` wait while it reads every search vector), the read functions `lb_search_corrections` and `lb_search_corrected` (grant them to an application role created later with `grant_read_functions`, as before), and drops the title trigram index of `0011`. At 1M Records typo-tolerant search takes 7.6 to 14 ms at p95 instead of 116 to 123 ms; the triggers add about 5% to a commit of 1,000 changes at 1M Records and about 12% at 100k ([performance](docs/performance.md#1m-records), [design 8.4](docs/design.md#84-search)).
- The performance harness (`tests/perf/bench.py`) reports p99 next to p50 and p95, times Record history and lineage, and with `--seed-database NAME` keeps the loaded dataset in its own database and measures a copy of it, so a run at 1M Records loads once. The 1M-Record run is in [performance](docs/performance.md#1m-records): every read is within budget except typo-tolerant title search (about 120 ms at p95 against 50 ms), the 2-hop neighborhood on branches other than `main` (29 to 34 ms against 30 ms) and lineage against the 10 ms proposed for it; creating or deleting a copy branch at that size takes longer than the default `database.statement_timeout_ms`.
- The web app Canvas lays large graphs out in a web worker instead of on the main thread: the graph is drawn at once and refined while it is on screen, the layout stops when it settles or at a time budget and can be paused, and large graphs use Barnes-Hut, hide edge labels and most node labels, and hide edges while panning. On a generated graph of 5,000 nodes and 10,000 edges the first render takes about 0.6 s instead of 1.7 s ([performance](docs/performance.md#web-app-canvas-5000-nodes-10000-edges)). The limits are configurable (`VITE_CANVAS_*`), and `pnpm perf:canvas` with `VITE_MOCK_PERF_NODES` measures a generated graph.
- Herald gives each Keeper request its own span: a request hook on the Keeper client sends a `traceparent` with a fresh span id whose parent is the span of the MCP tool call, in the caller's trace, so the requests of one tool call are told apart in the agent trace and in tracing backends. When an OpenTelemetry span is active in Herald, its context is propagated instead. The Python clients take `event_hooks`, passed to httpx ([agent trace](docs/agent-trace.md#herald)).

### Security

- Keeper sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `Referrer-Policy: no-referrer` and, over https (directly or from a proxy in `keeper.trusted_proxies` with `X-Forwarded-Proto: https`), `Strict-Transport-Security`; `keeper.security_headers` configures or turns them off. The web image sends a Content Security Policy whose `connect-src` holds the Keeper origin of the runtime configuration (`LOREBASE_WEB_CSP_CONNECT_SRC` adds sources, `LOREBASE_WEB_CSP` replaces the policy, `LOREBASE_WEB_HSTS` adds HSTS), and the Helm chart has the same through `web.security`. The web image's `Referrer-Policy` changes from `same-origin` to `no-referrer` ([deployment](docs/deployment.md)).
- The application role can no longer change the audit log: migration `0015` revokes `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` from `PUBLIC`, from `database.application_role` and from every other role but the table owner, and the compose `db-roles` script no longer grants them. Entries are still appended and read as before; nothing in Lorebase prunes the audit log, and an operator who must do so works as the owner ([deployment](docs/deployment.md#database-roles)).
- Document intake by URL no longer trusts the allowlisted host's DNS: Keeper resolves the host once, refuses it with 422 unless every address is global unicast (loopback, private, link-local, shared and other non-global ranges are refused, as for webhook targets), and connects only to the checked addresses, so a changed DNS answer cannot reach an internal service. `keeper.documents.url_allow_private_targets` (false) turns the check off for hosts on an internal network.
- Scribe parses PDF and DOCX documents in a child process without network access, stopped after `scribe.extraction.parser.timeout_s` (60 s) of wall-clock time, `cpu_s` (60) of CPU time or `memory_mb` (1024 MiB, where the system enforces address-space limits), and refuses documents above `max_input_bytes` (50 MiB). A crafted document that hits a limit fails its extraction job with a message naming the setting instead of holding the worker; `isolated: false` returns to parsing in a worker thread ([extraction](docs/extraction.md)).
- Webhook signing keys can be stored encrypted: with `webhooks.encryption_key` (a `secret://` reference to at least 32 characters, the same for Keeper and Scribe) new keys are sealed with AES-256-GCM, the delivery worker seals the keys stored before, and `previous_encryption_keys` lets the key change without breaking deliveries. Receivers change nothing. Migration `0016` adds `webhooks.sealed_key`; its downgrade refuses while sealed keys exist ([agents](docs/agents.md#webhooks)).
- Supply chain: the base images of the backend and web images (and the compose proxy image) are pinned by digest with the tag kept readable, and moved by hand ([release](docs/release.md#base-images)); the build arguments `PYTHON_TAG`, `NODE_TAG` and `NGINX_TAG` are replaced by `PYTHON_IMAGE`, `NODE_IMAGE` and `NGINX_IMAGE`. A CI workflow (`audit.yaml`) runs pip-audit on the locked Python dependencies and `pnpm audit --prod` on every pull request and weekly, failing on advisories not accepted in `.github/audit-allowlist.yaml`; `make security` uses the same check.
- The Helm chart no longer runs Keeper and Scribe as the owner of the tables. As on compose, it takes two DSNs: `db-maintenance-dsn` (`secrets.keys.dbMaintenanceDsn`, the owner) for the migration Job and for `database.maintenance_dsn` of Scribe and Keeper, and `db-dsn` for the application role (`database.appRole.name`, default `lorebase_app`) that Keeper and Scribe connect as, so row-level security, the append-only `audit_log` and the ban on DDL apply to them. A `db-roles` init container of the migration Job creates the role when missing (`database.appRole.create`, needs `CREATEROLE`) or waits for one created elsewhere, refuses `SUPERUSER`, `BYPASSRLS` or the owner, and applies the grants of the compose script; the migration runs with `database.application_role`. With the in-cluster Postgres the operator manages the role (`postgresql.cluster.roles`) with the password of `secrets.values.dbAppPassword`. The chart refuses one user for both DSNs unless `database.allowSharedRole: true` (development). Upgrading: add `db-maintenance-dsn` with the old DSN and point `db-dsn` at the application role; an in-cluster release upgrades once with `database.allowSharedRole=true`, then without ([Kubernetes](docs/kubernetes.md#database-roles)).

## 0.1.0 - 2026-10-21

First release. Lorebase keeps a typed ontology in Postgres and lets teams change it on branches, review the change in a Proposal and merge schema and data together, with Conflicts resolved per Attribute. Agents read through a REST API that never calls a model, or through the MCP server, and write only through Operations; a write that needs review becomes a task branch and a Proposal. Documents are extracted into Proposals whose items reviewers accept or reject. Pre-alpha and pre-1.0: `/api/v1` is not frozen and interfaces may change in a minor version. The database schema is at migration `0012`. The lines of this first section link the documentation of each feature; from the next release they link the pull request or issue.

### Added

Schema and versioning ([design](docs/design.md), [schema as code](examples/schema_as_code.md))

- A Domain is a YAML schema document (`format: lorebase.schema/v1`) with Kinds, Attributes, Relations, Traits, Operations, Derivations and Sources, checked statically and applied as one schema change set: `POST /api/v1/domains/{domain}/branches/{branch}/schema/changes`, `lorebase schema validate|diff|apply`. Attribute ids are stable, so a rename keeps its history.
- Content-addressed Revisions, branches, tags, diff and time-travel reads (`?at=<revision>`, `lorebase diff`, `lorebase record get --at`).
- Three-way merge of schema and data with typed Conflicts (attribute value, delete or modify, add or add, missing value, type coercion, cardinality, dangling Link and more), resolved with `ours`, `theirs`, `base` or a custom value, one by one or from a file (`lorebase proposal conflicts|resolve`). Merge policies `prefer`, cascade and defaults. The merged data is validated against the merged schema before the commit.
- Proposals with reviews, required approvals (`keeper.proposals`), Conflict resolution and merge over REST and CLI (`lorebase proposal create|review|merge|close`). The default branch of a Domain is protected (`keeper.domains.protect_default_branch`): changes reach it through a Proposal.
- Expressions in CEL for Operations (preconditions, steps, review policies) and for `expression` and `aggregate` Derivations, type checked when a schema is applied (`schema.expressions_enabled`) and recomputed in the materialized head on every commit. `path` Derivations are not computed.

Reads for people and agents ([agents](docs/agents.md), [performance](docs/performance.md))

- Records, Links, the JSON query DSL, traversal, neighborhoods and lexical search over REST (`lorebase record`, `query`, `search`), with ETags and the serving Revision in every response. Full-text search reads GIN indexes on `(domain_id, branch, search)` and `(domain_id, branch, title gin_trgm_ops)` (migration `0011`, `btree_gin`), so a search reads only its own branch's matches, however many branches share the partition. Semantic search takes vectors supplied by the caller; nothing computes embeddings.
- Context packs within a token budget (`POST .../context`, `lorebase context`), Record explanations with the origin of each value (`GET .../records/{key}/explain`, `lorebase explain`) and data health reports (`GET .../health`, `lorebase health`), all computed without a model.
- A change feed as Server-Sent Events and as polling (`GET .../branches/{branch}/events`, `.../changes`) and signed webhooks (`POST .../webhooks`, `Lorebase-Signature` HMAC).
- Overlay branches ([store schema notes](docs/store-schema-notes.md#overlay-branches), migration `0010`): a branch created with `mode: overlay` (`POST .../branches`, default `store.materialize.branch_mode`, always for names under `agent/`, `extract/` and `source/`, and for agent task branches per `keeper.agent_writes.branch_mode`) stores only the rows it changes and reads its base as of the fork point. Creating one does not depend on the size of the Domain; it is promoted to a full copy above `store.materialize.overlay_max_rows` rows or `overlay_max_base_lag_revisions` generations of base lag, before a schema change and before its base is deleted. `lorebase branch create --mode copy|overlay` chooses the mode from the command line. Overlay reads go through `_overlay` variants of the security definer functions with the same argument and scope checks. An overlay gets the per-Attribute indexes of its schema on its own rows, built as `store.index` jobs when it is created, and its neighborhood looks Links and Records up with one index scan over both branches (migration `0012`); on the 100k-Record baseline search, attribute queries, Links of a Record and the neighborhood stay within 30% of a copy at p50 ([performance](docs/performance.md#overlay-branches-milliseconds)).
- Per-Attribute indexes and security definer read functions that keep Domain isolation under row-level security. At 99,900 Records and 302,940 Links on one laptop, the measured p95 of every agent read stays within its budget ([performance](docs/performance.md)); the 1M-Record baseline is not measured.

Writes and ingestion ([quickstart](docs/quickstart.md), [scribe](docs/scribe.md), [inference](docs/inference.md))

- Built-in Operations `import_records`, `import_links` and `import_batch` with dry run and idempotency keys, and custom Operations declared in the schema (`POST .../operations/{operation}/execute`).
- `lorebase import records|links|batch` load CSV, TSV, JSON Lines or JSON (Parquet with the `parquet` extra): types are converted from the schema, a Record travels with its Links, files are cut into batches of one Revision each.
- Schema inference from CSV, TSV, JSON, JSON Lines (`.jsonl`, `.ndjson`) and Parquet uploads, chosen by suffix (`keeper.schema_inference.file_formats`), and from Postgres tables (`POST .../schema:infer`): Kinds, typed Attributes, keys, Relations with cardinality, a confidence and the evidence for every decision. It proposes and writes nothing. Parquet uploads need the `lorebase-keeper[parquet]` extra; without it they are refused with a 422 naming it. A record profiler (`lorebase_store.profiling.profile_records`, `RecordProfiler`) and `profile_source` in Scribe profile any Source through its connector; limits are in `store.profiling.records`.
- CSV and Postgres Sources with snapshot and incremental syncs run by Scribe, the worker and scheduler on the Postgres job queue. A sync commits on a Source branch, opens a Proposal and applies the Source's merge policy (`proposal`, `auto_when_clean`, `auto_with_authority`); every changed value keeps its row as Lineage (`lorebase sources sync|runs`).
- JSON, JSON Lines, Parquet and HTTP JSON Sources ([scribe](docs/scribe.md#sources)): the `json` and `jsonl` types and the `records_path`, `flatten_separator` and `http` options (headers as secret references, cursor, page, offset or Link header pagination, a watermark parameter and a page cap). Files are opened under the allowed roots without following links, URLs are checked against private addresses, JSON Lines and Parquet are streamed, and an HTTP JSON run that passes `max_pages` fails instead of committing part of a snapshot. Parquet needs the `lorebase-scribe[parquet]` extra.
- Document intake and tiered extraction into Proposals ([extraction](docs/extraction.md)): `POST .../documents` takes Markdown, plain text, PDF and DOCX (PDF and DOCX with the scribe `documents` extra); Scribe parses and chunks them and proposes Records, Links and values with verified evidence, from rules (tier 0, no model), local GLiNER and GLiREL (tier 1) or any OpenAI-compatible model with JSON schema output (tier 2, cached, token budget per job). Reviewers accept, edit or reject items one by one or by filter (`GET .../proposals/{p}/items`, `POST .../items:decide`, `lorebase documents upload`, `lorebase proposal items|decide`); nothing reaches the default branch without a merge. Derived and sensitive Attributes are never extracted. `GET .../documents/{id}/text` (`lorebase documents text`) serves the parsed text the evidence offsets index. The web app has a Documents screen (intake, library, a viewer that highlights the evidence in the parsed text) and an Items tab on extraction Proposals to accept, edit or reject items one by one or by filter.
- Inference providers behind one OpenAI-compatible interface for chat and embeddings, plus local fastembed, GLiNER and GLiREL (optional extras), and compose profiles for Ollama and a LiteLLM proxy. Extraction uses them; nothing computes embeddings yet.

Agents and access ([MCP](docs/mcp.md), [operations](docs/operations.md))

- Herald, the MCP server, over stdio and Streamable HTTP with 11 tools (`lorebase_context`, `lorebase_query`, `lorebase_execute` with dry run and more), two resources and one prompt. It is a thin layer over Keeper and holds no database credentials. `lorebase_execute` passes `intent`, `auto_propose` and `auto_merge` to Keeper also when the call names no `task`, and returns Keeper's problem text unchanged; `auto_propose: true` without a `task` is refused as `validation-failed`.
- Agent writes that need review ([agents](docs/agents.md#writes-that-need-review)): an Operation refused with `409 review-required` (protected branch or review policy) runs, when the call names a `task`, on a task branch `agent/{principal}/{task}` and opens or updates one Proposal, merged at once only when `keeper.agent_writes.allowed_roles_for_auto_merge` allows the caller's role, nothing conflicts and the required approvals are in. Without a `task` the `409` carries `next` hints. Settings `keeper.agent_writes`, overridable per Domain.
- API keys (hashed with a server-side pepper), OIDC bearer tokens, role grants per Domain, Kind, Operation and branch, and a hash-chained audit log (`lorebase apikey`, `GET .../audit`). `python -m lorebase_keeper bootstrap` creates the first installation administrator key from the database settings and prints it once; it refuses when an administrator already holds a usable key, unless `--force`.
- Rate limits per principal and request class (`RateLimit-*` headers, `429` with `Retry-After`) and daily quotas per API key, shown by `lorebase whoami` (`keeper.limits.rate`, `keeper.limits.quota`). Failed authentications are counted per client address and per key prefix; `keeper.limits.rate.auth_failures.per_key_prefix_enabled: false` counts them per client address only, so that someone who knows a key prefix cannot keep that key throttled.
- Domain backup and restore bundles (`python -m lorebase_store.bundle export|import`) and garbage collection of unreachable Revisions with a dry run (`python -m lorebase_store.gc`).

Clients and web app ([web app](apps/web/README.md), [tour](docs/tour.md))

- The `lorebase` command line and a Python client, sync and async, checked against the committed OpenAPI document ([docs/openapi.json](docs/openapi.json)). Exit codes are documented: 0 success, 1 usage or not found, 2 validation or conflict, 3 authentication or permission, 4 server error.
- A web app with Explorer, Canvas, Modeler (including a Start from data wizard over schema inference that accepts CSV, TSV, JSON, JSON Lines and Parquet files), Review with a Conflict resolver and an Items tab for extraction Proposals, Documents, Sources and Admin screens. It runs on the mock API or on Keeper, with end-to-end tests against a real Keeper for browsing, Branches, schema changes, Review and Settings. It reads `/config.js` (`window.__LOREBASE_CONFIG__`: `apiMode`, `keeperBaseUrl`, an optional `apiToken` or any `VITE_*` name) over its build values, so the `lorebase-web` image switches to live mode at run time, from `VITE_*` variables of the container or the chart's `web.config`. Screens load on demand: the main chunk is 193 kB, vendor libraries sit in their own chunks, and `pnpm build` fails when the main chunk or the first load exceeds `apps/web/bundle-budget.json`. The Modeler and the Sources editor keep the Source options they do not show when they save a schema.
- The five-day demo: `make demo` brings up a dedicated compose stack and runs the proof scenario of [design 3.2](docs/design.md#32-the-5-day-proof-scenario) with the CLI, in under a minute once the image is built ([docs/demo.md](docs/demo.md)).

### Security

- A security review of the trust boundaries before this release ([docs/security-review.md](docs/security-review.md)) fixed all 23 findings, among them: a Source could resolve any secret reference, including the database DSN (critical), Source errors echoed resolved secrets, `keeper.auth.mode: none` could be served on a non-loopback address (now refused unless `keeper.auth.allow_insecure`), webhook targets in non-global address ranges were accepted, and a slow webhook target could stall delivery for every Domain.
- Compose: Keeper and Scribe connect as an application role without superuser or `BYPASSRLS` (`LOREBASE_APP_USER`, `LOREBASE_APP_PASSWORD`, created by the one-shot `db-roles`), so row-level security applies to them; the owner role runs the migrations and index maintenance. The `litellm` and `observability` profiles refuse to start while `LITELLM_MASTER_KEY` or `GRAFANA_ADMIN_PASSWORD` is empty, `change-me` or shorter than 16 characters.
- Migration `0008` adds argument, scope and `search_path` checks to the security definer read functions and refuses to run while the application role may create objects in their schemas; migration `0009` adds client network allowlists to API keys (`allowed_networks`, `lorebase apikey create --allow-network`, behind `keeper.trusted_proxies`).
- Bundle import is bounded and refuses links, schema inference sources are configured per Domain, the OIDC issuer and signing keys need `https`, CSV Sources check the resolved address and open files without following links, failed authentications are rate limited per client address and key prefix, the Helm NetworkPolicy is on by default with narrow egress, provider error text is scrubbed, and open event streams are authorized again at an interval.

### Not done yet

- Lineage and history endpoints beyond the lineage summary on Record reads.
- The 1M-Record performance baseline and the 10M-Record targets of the design.
- Merge policies `authority` and `newest_wins`.
- Schema suggestions from extraction; embedding jobs and hybrid search (semantic search ranks stored vectors against a query vector the caller supplies); `path` Derivations.
- Events declared by Operations (the outbox and signed webhooks carry Revision events only), sensitivity masking, the PII vault, and Traits in time-travel reads.
- Web app: OIDC login with BFF sessions, the Operation, Derivation and Source editors of the Modeler, and a Canvas that renders 5k nodes and 10k edges smoothly.
- A command or endpoint that verifies the audit chain, LinkML import and export, the threat model, the proof scenario as an automated test in CI, and the stability promise for `/api/v1` that comes with 1.0.

### Upgrade notes

There is no earlier release. For a new installation, run the migrations (`alembic upgrade head`, migrations `0001` to `0012`) before Keeper starts: the compose `migrate` service and the Helm hook do it. Migration `0011` creates the `btree_gin` extension when it is missing (it ships with Postgres contrib); on a database that already holds data it builds the search indexes concurrently per partition, without blocking writes. Keeper's shipped configuration accepts every request as an administrator (`keeper.auth.mode: none`); use `api_key` or `oidc` for anything shared, give `api_key` modes a pepper of at least 32 characters, list the administrator in `keeper.auth.installation_admins` and create the first key with `python -m lorebase_keeper bootstrap`.
