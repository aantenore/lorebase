# Changelog

What changed in each release, newest first. The notes are written for the person deciding whether to upgrade; the rules are in [docs/launch/changelog-style.md](docs/launch/changelog-style.md). Lorebase follows semantic versioning. Before 1.0, any minor version may change an interface, and the notes say so.

## Unreleased

### Added

- The embedding model of a Domain is advertised to agents: `GET /api/v1/domains/{domain}/schema` has a `search` block with the search `modes` and, when a Kind has `search.embedding_template`, `embedding` (`model`, `dims`) read from `search.semantic.model` and `store.embeddings.dims`; `lorebase_schema` shows it as a `SEARCH` line, and the Python client has `SchemaDocument.search`.
- `inference.embeddings.query_prefix` and `document_prefix` (empty by default) for models trained with prefixes, such as E5: `lorebase-inference embed --query TEXT` puts the query prefix before the text, and Scribe puts the document prefix before every embedded Record text. Changing the document prefix makes the next pass embed every text again. `lorebase-inference embed TEXT` without `--query` no longer adds anything, which is what it did before prefixes existed ([inference providers](docs/inference-providers.md#embeddings-for-search)).
- Garbage collection deletes the embeddings no branch head references (for example the vectors of Records that only a deleted branch held); `python -m lorebase_store.gc --dry-run` and the `gc` job report their count as `embeddings` ([operations](docs/operations.md#garbage-collection)).
- The Modeler edits `search.embedding_template` and `search.embedding_sensitive` on the Kind form, checks the placeholders against the Kind's Attributes (unknown, derived and sensitive ones) before a change is sent, and follows an Attribute rename in the template.
- Embedding jobs for semantic and hybrid search. A Kind opts in with `search.embedding_template` in the schema (`{attribute}` placeholders by api name, plus `{_kind}` and `{_key}`; sensitive Attributes only with `search.embedding_sensitive: true`; invalid templates are reported as `schema.embedding_template_invalid`). Scribe's scheduler queues an `embeddings` job per Domain every `scribe.scheduler.embeddings_interval_s` (60 s): it embeds, branch by branch, the Records that lack a vector of the configured `inference.embeddings` model, re-renders the Kinds whose template changed, skips texts whose hash did not change and copies the vector of an identical text instead of calling the model. Vectors stay keyed by content hash, so overlay and copied branches only add work for the Records they change. Batching, a row budget per job with resumable continuations, call pacing and retries come from the new `scribe.embeddings` settings; the model's dimension is checked against `store.embeddings.dims` before the first call. `lorebase-scribe embeddings DOMAIN [--branch B] [--reindex] [--prune]` backfills, reindexes and, after a model switch, deletes the vectors of other models. New metrics `lorebase.scribe.embeddings.records` and `lorebase.scribe.embeddings.call.duration`. Migration `0014` adds `embeddings.text_hash` and the `embedding_cursors` table ([scribe](docs/scribe.md#embeddings)).
- Query vectors on the caller's side, since Keeper and Herald never call a model: `lorebase-inference embed TEXT` prints the vector of the configured embedding model, and `lorebase search TEXT --vector-file FILE` (`-` for standard input) sends it for hybrid search ([inference providers](docs/inference-providers.md#embeddings-for-search)).
- Per-Record history and lineage: `GET /api/v1/domains/{domain}/kinds/{kind}/records/{key}/history` lists the Revisions that changed a Record on a branch, newest first, with the changed Attributes, their provenance and, with `values=true`, the values before and after; `GET .../records/{key}/lineage` tells per Attribute where the current value came from (provenance, Revision, Source, Operation, extraction evidence, Proposal). Both read one index range of the branch history, are authorized and cached like Record reads, and are bounded by the new `read.history` settings. Also in the Python client (`records.history`, `records.lineage`), the CLI (`lorebase record history|lineage`), the MCP server (`lorebase_history`, `lorebase_lineage`) and the History tab of the Explorer Record page.
- Merge policies `authority` and `newest_wins` ([design 6.10](docs/design.md#610-resolution-flows)). `authority` (globally or per Attribute in `authority_attributes`) is a ranked list of origins such as `source:<id>`, `principal:<id>`, `actor:<id>` or `origin:extraction`: on an attribute value Conflict the side whose last change comes from the higher ranked origin wins, and `schema_authority: true` ranks an Attribute's schema `authority` Source first. `newest_wins` (or `newest_wins_attributes`) takes the side whose last change has the later provenance time, equal times going to the greater provenance id. Both read the Lineage of both branches, leave the Conflict to a person when they cannot decide, and record why they decided in the attempt's `auto_resolutions[].details`, which the Review screen shows. Set them in the Domain's `merge_policy` setting; Source merges apply them too.
- Sign-in for the web app with Keeper as backend-for-frontend (`keeper.auth.sessions`, off by default; needs an `oidc` auth mode). `GET /api/v1/auth/login` runs the OpenID Connect authorization code flow with PKCE against the configured provider, `GET /auth/callback` checks state, nonce and the ID token and sets an opaque `HttpOnly`, `SameSite=Lax` session cookie (`__Host-` prefixed and `Secure` unless `cookie_secure: false`), `GET /auth/session` returns the user and the session's CSRF token, and `POST /auth/logout` ends the session and returns the provider's end-session URL. Sessions live in the new `web_sessions` table (migration `0013`; only a SHA-256 of the session id is stored, provider tokens are encrypted with `sessions.encryption_key`) with idle and absolute timeouts, a new id on every sign-in and refresh-token checks at the provider. A session maps to the same principal, groups and grants as the user's bearer tokens; POST, PUT, PATCH and DELETE with the cookie need the CSRF header, a trusted `Origin` and no cross-site `Sec-Fetch-Site`. API keys, bearer tokens and `auth.mode: none` work as before. The web app gets `VITE_AUTH_MODE=session` (`authMode` in `/config.js`): a sign-in screen at `/login`, a sign-out button, cookie requests with the CSRF header, and a redirect to sign-in on 401 ([deployment](docs/deployment.md#web-sign-in)).
- Operation, Derivation and Source editors in the web app Modeler ([tour](docs/tour.md#edit-schema)). Operations: typed parameters, preconditions, steps with their Kind or Relation and values, review policy, permissions, side effects, rate limit, and a dry run of the saved Operation on the Branch. Derivations: `expression`, `aggregate` and `path` variants, with the computed Attribute picked from the schema. Sources: the fields of each type (`records_path`, `flatten_separator`, `http` headers and pagination for `http_json`), `secret://` references only for connections and credential headers, key, Attribute and Relation mapping, sync mode with watermark, schedule and merge policy. Expressions are edited in a CEL editor, and the findings of Keeper's dry run, the CEL type check included when `schema.expressions_enabled` is on, appear next to the field. Edits go through the same change set, Branch and Proposal flow as the other editors, and keys a form does not edit stay as the YAML has them.
- Helm chart values for the web sign-in: `config.keeper.auth.sessions` settings, the OIDC client secret and the session encryption key read from the Secret (`secrets.keys.oidcClientSecret`, `secrets.keys.sessionEncryptionKey`, or `secrets.values.*` for a chart-managed one) and wired as `secret://env` references, `web.config.authMode: session`, render-time checks, and the `ci/sessions-values.yaml` overlay ([Kubernetes](docs/kubernetes.md#web-sign-in)).
- Audit chain verification ([operations](docs/operations.md#audit-chain-verification)). `python -m lorebase_keeper audit verify DOMAIN|--installation|--all` recomputes the hash chains of the audit log with the maintenance DSN, prints the first entry that does not verify (or JSON with `--json`) and exits 1 when there is one; `--after-seq` resumes from the `last_seq` of an earlier run. `GET /api/v1/domains/{domain}/audit/verify` (permission `audit.read`) and `lorebase audit verify` (exit code 2 on a broken chain) check one Domain's chain, and the Python client has `audit.verify`. Entries are read in batches, so memory does not grow with the log. Scribe queues an `audit_verify` job of every chain each `scribe.scheduler.audit_verify_interval_s` (one day; 0 disables it), counted in the new metric `lorebase.audit.verifications` by outcome, and the `LorebaseAuditChainBroken` alert fires when a chain is broken.
- A [threat model](docs/threat-model.md): STRIDE per trust boundary (web sign-in, API keys and OIDC, authorization in Keeper, Scribe connectors and document intake, Herald, Postgres roles and row-level security, webhooks, inference providers, the release pipeline), each mitigation with the file that implements it, and the residual risks in order of priority.
- An [API stability policy](docs/api-stability.md) for `/api/v1`: what is stable, which changes are compatible or breaking, the deprecation process with `Deprecation` and `Sunset` headers (none is deprecated yet, so Keeper sends neither), client compatibility, MCP tool stability and the `lorebase.schema/v1` format. It binds from 1.0; before it, breaking changes are named in the changelog.

### Changed

- The performance harness (`tests/perf/bench.py`) reports p99 next to p50 and p95, times Record history and lineage, and with `--seed-database NAME` keeps the loaded dataset in its own database and measures a copy of it, so a run at 1M Records loads once. The 1M-Record run is in [performance](docs/performance.md#1m-records): every read is within budget except typo-tolerant title search (about 120 ms at p95 against 50 ms), the 2-hop neighborhood on branches other than `main` (29 to 34 ms against 30 ms) and lineage against the 10 ms proposed for it; creating or deleting a copy branch at that size takes longer than the default `database.statement_timeout_ms`.
- The web app Canvas lays large graphs out in a web worker instead of on the main thread: the graph is drawn at once and refined while it is on screen, the layout stops when it settles or at a time budget and can be paused, and large graphs use Barnes-Hut, hide edge labels and most node labels, and hide edges while panning. On a generated graph of 5,000 nodes and 10,000 edges the first render takes about 0.6 s instead of 1.7 s ([performance](docs/performance.md#web-app-canvas-5000-nodes-10000-edges)). The limits are configurable (`VITE_CANVAS_*`), and `pnpm perf:canvas` with `VITE_MOCK_PERF_NODES` measures a generated graph.

### Security

- Keeper sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `Referrer-Policy: no-referrer` and, over https (directly or from a proxy in `keeper.trusted_proxies` with `X-Forwarded-Proto: https`), `Strict-Transport-Security`; `keeper.security_headers` configures or turns them off. The web image sends a Content Security Policy whose `connect-src` holds the Keeper origin of the runtime configuration (`LOREBASE_WEB_CSP_CONNECT_SRC` adds sources, `LOREBASE_WEB_CSP` replaces the policy, `LOREBASE_WEB_HSTS` adds HSTS), and the Helm chart has the same through `web.security`. The web image's `Referrer-Policy` changes from `same-origin` to `no-referrer` ([deployment](docs/deployment.md)).
- The application role can no longer change the audit log: migration `0015` revokes `UPDATE`, `DELETE` and `TRUNCATE` on `audit_log` from `PUBLIC`, from `database.application_role` and from every other role but the table owner, and the compose `db-roles` script no longer grants them. Entries are still appended and read as before; nothing in Lorebase prunes the audit log, and an operator who must do so works as the owner ([deployment](docs/deployment.md#database-roles)).
- Document intake by URL no longer trusts the allowlisted host's DNS: Keeper resolves the host once, refuses it with 422 unless every address is global unicast (loopback, private, link-local, shared and other non-global ranges are refused, as for webhook targets), and connects only to the checked addresses, so a changed DNS answer cannot reach an internal service. `keeper.documents.url_allow_private_targets` (false) turns the check off for hosts on an internal network.
- Scribe parses PDF and DOCX documents in a child process without network access, stopped after `scribe.extraction.parser.timeout_s` (60 s) of wall-clock time, `cpu_s` (60) of CPU time or `memory_mb` (1024 MiB, where the system enforces address-space limits), and refuses documents above `max_input_bytes` (50 MiB). A crafted document that hits a limit fails its extraction job with a message naming the setting instead of holding the worker; `isolated: false` returns to parsing in a worker thread ([extraction](docs/extraction.md)).
- Webhook signing keys can be stored encrypted: with `webhooks.encryption_key` (a `secret://` reference to at least 32 characters, the same for Keeper and Scribe) new keys are sealed with AES-256-GCM, the delivery worker seals the keys stored before, and `previous_encryption_keys` lets the key change without breaking deliveries. Receivers change nothing. Migration `0016` adds `webhooks.sealed_key`; its downgrade refuses while sealed keys exist ([agents](docs/agents.md#webhooks)).
- Supply chain: the base images of the backend and web images (and the compose proxy image) are pinned by digest with the tag kept readable, and moved by hand ([release](docs/release.md#base-images)); the build arguments `PYTHON_TAG`, `NODE_TAG` and `NGINX_TAG` are replaced by `PYTHON_IMAGE`, `NODE_IMAGE` and `NGINX_IMAGE`. A CI workflow (`audit.yaml`) runs pip-audit on the locked Python dependencies and `pnpm audit --prod` on every pull request and weekly, failing on advisories not accepted in `.github/audit-allowlist.yaml`; `make security` uses the same check.

## 0.1.0 - 2026-10-21

First release. Lorebase keeps a typed ontology in Postgres and lets teams change it on branches, review the change in a Proposal and merge schema and data together, with Conflicts resolved per Attribute. Agents read through a REST API that never calls a model, or through the MCP server, and write only through Operations; a write that needs review becomes a task branch and a Proposal. Documents are extracted into Proposals whose items reviewers accept or reject. Pre-alpha and pre-1.0: `/api/v1` is not frozen and interfaces may change in a minor version. The database schema is at migration `0012`. The lines of this first section link the documentation of each feature; from the next release they link the pull request or issue.

### Added

Schema and versioning ([design](docs/design.md), [schema as code](examples/schema_as_code.md))

- A Domain is a YAML schema document (`format: lorebase.schema/v1`) with Kinds, Attributes, Relations, Traits, Operations, Derivations and Sources, checked statically and applied as one schema change set: `POST /api/v1/domains/{domain}/branches/{branch}/schema/changes`, `lorebase schema validate|diff|apply`. Attribute ids are stable, so a rename keeps its history.
- Content-addressed Revisions, branches, tags, diff and time-travel reads (`?at=<revision>`, `lorebase diff`, `lorebase record get --at`).
- Three-way merge of schema and data with typed Conflicts (attribute value, delete or modify, add or add, missing value, type coercion, cardinality, dangling Link and more), resolved with `ours`, `theirs`, `base` or a custom value, one by one or from a file (`lorebase proposal conflicts|resolve`). Merge policies `prefer`, cascade and defaults. The merged data is validated against the merged schema before the commit.
- Proposals with reviews, required approvals (`keeper.proposals`), Conflict resolution and merge over REST and CLI (`lorebase proposal create|review|merge|close`). The default branch of a Domain is protected (`keeper.domains.protect_default_branch`): changes reach it through a Proposal.
- Expressions in CEL for Operations (preconditions, steps, review policies) and for `expression` and `aggregate` Derivations, type checked when a schema is applied (`schema.expressions_enabled`) and recomputed in the materialized head on every commit. `path` Derivations are not computed.

Reads for people and agents ([agents](docs/agents.md), [performance](docs/performance.md))

- Records, Links, the JSON query DSL, traversal, neighborhoods and lexical search over REST (`lorebase record`, `query`, `search`), with ETags and the serving Revision in every response. Full-text search reads GIN indexes on `(domain_id, branch, search)` and `(domain_id, branch, title gin_trgm_ops)` (migration `0011`, `btree_gin`), so a search reads only its own branch's matches, however many branches share the partition. Semantic search takes vectors supplied by the caller; nothing computes embeddings.
- Context packs within a token budget (`POST .../context`, `lorebase context`), Record explanations with the origin of each value (`GET .../records/{key}/explain`, `lorebase explain`) and data health reports (`GET .../health`, `lorebase health`), all computed without a model.
- A change feed as Server-Sent Events and as polling (`GET .../branches/{branch}/events`, `.../changes`) and signed webhooks (`POST .../webhooks`, `Lorebase-Signature` HMAC).
- Overlay branches ([store schema notes](docs/store-schema-notes.md#overlay-branches), migration `0010`): a branch created with `mode: overlay` (`POST .../branches`, default `store.materialize.branch_mode`, always for names under `agent/`, `extract/` and `source/`, and for agent task branches per `keeper.agent_writes.branch_mode`) stores only the rows it changes and reads its base as of the fork point. Creating one does not depend on the size of the Domain; it is promoted to a full copy above `store.materialize.overlay_max_rows` rows or `overlay_max_base_lag_revisions` generations of base lag, before a schema change and before its base is deleted. `lorebase branch create --mode copy|overlay` chooses the mode from the command line. Overlay reads go through `_overlay` variants of the security definer functions with the same argument and scope checks. An overlay gets the per-Attribute indexes of its schema on its own rows, built as `store.index` jobs when it is created, and its neighborhood looks Links and Records up with one index scan over both branches (migration `0012`); on the 100k-Record baseline search, attribute queries, Links of a Record and the neighborhood stay within 30% of a copy at p50 ([performance](docs/performance.md#overlay-branches-milliseconds)).
- Per-Attribute indexes and security definer read functions that keep Domain isolation under row-level security. At 99,900 Records and 302,940 Links on one laptop, the measured p95 of every agent read stays within its budget ([performance](docs/performance.md)); the 1M-Record baseline is not measured.

Writes and ingestion ([quickstart](docs/quickstart.md), [scribe](docs/scribe.md), [inference](docs/inference.md))

- Built-in Operations `import_records`, `import_links` and `import_batch` with dry run and idempotency keys, and custom Operations declared in the schema (`POST .../operations/{operation}/execute`).
- `lorebase import records|links|batch` load CSV, TSV, JSON Lines or JSON (Parquet with the `parquet` extra): types are converted from the schema, a Record travels with its Links, files are cut into batches of one Revision each.
- Schema inference from CSV, TSV, JSON, JSON Lines (`.jsonl`, `.ndjson`) and Parquet uploads, chosen by suffix (`keeper.schema_inference.file_formats`), and from Postgres tables (`POST .../schema:infer`): Kinds, typed Attributes, keys, Relations with cardinality, a confidence and the evidence for every decision. It proposes and writes nothing. Parquet uploads need the `lorebase-keeper[parquet]` extra; without it they are refused with a 422 naming it. A record profiler (`lorebase_store.profiling.profile_records`, `RecordProfiler`) and `profile_source` in Scribe profile any Source through its connector; limits are in `store.profiling.records`.
- CSV and Postgres Sources with snapshot and incremental syncs run by Scribe, the worker and scheduler on the Postgres job queue. A sync commits on a Source branch, opens a Proposal and applies the Source's merge policy (`proposal`, `auto_when_clean`, `auto_with_authority`); every changed value keeps its row as Lineage (`lorebase sources sync|runs`).
- JSON, JSON Lines, Parquet and HTTP JSON Sources ([scribe](docs/scribe.md#sources)): the `json` and `jsonl` types and the `records_path`, `flatten_separator` and `http` options (headers as secret references, cursor, page, offset or Link header pagination, a watermark parameter and a page cap). Files are opened under the allowed roots without following links, URLs are checked against private addresses, JSON Lines and Parquet are streamed, and an HTTP JSON run that passes `max_pages` fails instead of committing part of a snapshot. Parquet needs the `lorebase-scribe[parquet]` extra.
- Document intake and tiered extraction into Proposals ([extraction](docs/extraction.md)): `POST .../documents` takes Markdown, plain text, PDF and DOCX (PDF and DOCX with the scribe `documents` extra); Scribe parses and chunks them and proposes Records, Links and values with verified evidence, from rules (tier 0, no model), local GLiNER and GLiREL (tier 1) or any OpenAI-compatible model with JSON schema output (tier 2, cached, token budget per job). Reviewers accept, edit or reject items one by one or by filter (`GET .../proposals/{p}/items`, `POST .../items:decide`, `lorebase documents upload`, `lorebase proposal items|decide`); nothing reaches the default branch without a merge. Derived and sensitive Attributes are never extracted. `GET .../documents/{id}/text` (`lorebase documents text`) serves the parsed text the evidence offsets index. The web app has a Documents screen (intake, library, a viewer that highlights the evidence in the parsed text) and an Items tab on extraction Proposals to accept, edit or reject items one by one or by filter.
- Inference providers behind one OpenAI-compatible interface for chat and embeddings, plus local fastembed, GLiNER and GLiREL (optional extras), and compose profiles for Ollama and a LiteLLM proxy. Extraction uses them; nothing computes embeddings yet.

Agents and access ([MCP](docs/mcp.md), [operations](docs/operations.md))

- Herald, the MCP server, over stdio and Streamable HTTP with 11 tools (`lorebase_context`, `lorebase_query`, `lorebase_execute` with dry run and more), two resources and one prompt. It is a thin layer over Keeper and holds no database credentials. `lorebase_execute` passes `intent`, `auto_propose` and `auto_merge` to Keeper also when the call names no `task`, and returns Keeper's problem text unchanged; `auto_propose: true` without a `task` is refused as `validation-failed`.
- Agent writes that need review ([agents](docs/agents.md#writes-that-need-review)): an Operation refused with `409 review-required` (protected branch or review policy) runs, when the call names a `task`, on a task branch `agent/{principal}/{task}` and opens or updates one Proposal, merged at once only when `keeper.agent_writes.allowed_roles_for_auto_merge` allows the caller's role, nothing conflicts and the required approvals are in. Without a `task` the `409` carries `next` hints. Settings `keeper.agent_writes`, overridable per Domain.
- API keys (hashed with a server-side pepper), OIDC bearer tokens, role grants per Domain, Kind, Operation and branch, and a hash-chained audit log (`lorebase apikey`, `GET .../audit`). `python -m lorebase_keeper bootstrap` creates the first installation administrator key from the database settings and prints it once; it refuses when an administrator already holds a usable key, unless `--force`.
- Rate limits per principal and request class (`RateLimit-*` headers, `429` with `Retry-After`) and daily quotas per API key, shown by `lorebase whoami` (`keeper.limits.rate`, `keeper.limits.quota`). Failed authentications are counted per client address and per key prefix; `keeper.limits.rate.auth_failures.per_key_prefix_enabled: false` counts them per client address only, so that someone who knows a key prefix cannot keep that key throttled.
- Domain backup and restore bundles (`python -m lorebase_store.bundle export|import`) and garbage collection of unreachable Revisions with a dry run (`python -m lorebase_store.gc`).

Clients and web app ([web app](apps/web/README.md), [tour](docs/tour.md))

- The `lorebase` command line and a Python client, sync and async, checked against the committed OpenAPI document ([docs/openapi.json](docs/openapi.json)). Exit codes are documented: 0 success, 1 usage or not found, 2 validation or conflict, 3 authentication or permission, 4 server error.
- A web app with Explorer, Canvas, Modeler (including a Start from data wizard over schema inference that accepts CSV, TSV, JSON, JSON Lines and Parquet files), Review with a Conflict resolver and an Items tab for extraction Proposals, Documents, Sources and Admin screens. It runs on the mock API or on Keeper, with end-to-end tests against a real Keeper for browsing, Branches, schema changes, Review and Settings. It reads `/config.js` (`window.__LOREBASE_CONFIG__`: `apiMode`, `keeperBaseUrl`, an optional `apiToken` or any `VITE_*` name) over its build values, so the `lorebase-web` image switches to live mode at run time, from `VITE_*` variables of the container or the chart's `web.config`. Screens load on demand: the main chunk is 193 kB, vendor libraries sit in their own chunks, and `pnpm build` fails when the main chunk or the first load exceeds `apps/web/bundle-budget.json`. The Modeler and the Sources editor keep the Source options they do not show when they save a schema.
- The five-day demo: `make demo` brings up a dedicated compose stack and runs the proof scenario of [design 3.2](docs/design.md#32-the-5-day-proof-scenario) with the CLI, in under a minute once the image is built ([docs/demo.md](docs/demo.md)).

Deployment ([deployment](docs/deployment.md), [kubernetes](docs/kubernetes.md))

- Docker compose for Postgres 16 with pgvector, migrations, Keeper and Scribe, with profiles `local-models`, `litellm`, `observability` and `scale-out` (a second Keeper, a Postgres streaming replica and nginx; read replica routing with a freshness guard).
- A Helm chart (`deploy/helm/lorebase`) for Keeper, a migration hook, Scribe, Herald, the web app, Ollama, Ingress, autoscaling and read replica DSNs. The Postgres parameters of the CloudNativePG cluster are explicit (`postgresql.cluster.postgresql.parameters`, `max_connections: "100"` by default); size it above Keepers x (`pool_size` + `max_overflow`) plus Scribe, migrations and administration. It passes `helm lint --strict`, `helm template` and kubeconform; it has not run on a live cluster.
- An observability bundle in `deploy/observability`: Grafana dashboards for Keeper, Store and Scribe, Prometheus alert rules with a runbook per alert and the OpenTelemetry Collector configuration ([operations](docs/operations.md#dashboards-and-alerts)). The compose `observability` profile loads them; the Helm chart renders them as ConfigMaps with `observability.enabled=true`.
- A metrics catalogue ([docs/metrics.md](docs/metrics.md)) with the Prometheus series, labels and source of every metric, among them the response cache, authentication failures, commit duration, merge attempts, security definer read calls, jobs claimed and queue depth, webhook deliveries, garbage collection runs and bytes freed, and extraction items. A test fails when a dashboard or alert rule names a series that is not emitted, or when an instrument is missing from the catalogue. Latency histograms declare explicit bucket boundaries from 5 ms to 10 s.
- Release artifacts: images `ghcr.io/aantenore/lorebase` (Keeper, Scribe and Herald share it; the command picks the service) and `ghcr.io/aantenore/lorebase-web`, tagged `0.1.0`, `0.1` and `latest`, signed with cosign keyless and carrying a CycloneDX SBOM attestation; CycloneDX SBOMs and the Helm chart package on the GitHub release. The nine Python workspace packages go to PyPI only when the maintainers configured publishing.

Documentation

- A documentation site at [aantenore.github.io/lorebase](https://aantenore.github.io/lorebase/), built from `docs/` with Material for MkDocs (`make docs`, `make docs-serve`) and published on every push to `main`. The command line and configuration reference pages are generated from the code (`make docs-generate`; `scripts/docs/generate.py --check` fails on a stale page) and the REST API page renders the committed `docs/openapi.json`.

### Security

- A security review of the trust boundaries before this release ([docs/security-review.md](docs/security-review.md)) fixed all 23 findings, among them: a Source could resolve any secret reference, including the database DSN (critical), Source errors echoed resolved secrets, `keeper.auth.mode: none` could be served on a non-loopback address (now refused unless `keeper.auth.allow_insecure`), webhook targets in non-global address ranges were accepted, and a slow webhook target could stall delivery for every Domain.
- Compose: Keeper and Scribe connect as an application role without superuser or `BYPASSRLS` (`LOREBASE_APP_USER`, `LOREBASE_APP_PASSWORD`, created by the one-shot `db-roles`), so row-level security applies to them; the owner role runs the migrations and index maintenance. The `litellm` and `observability` profiles refuse to start while `LITELLM_MASTER_KEY` or `GRAFANA_ADMIN_PASSWORD` is empty, `change-me` or shorter than 16 characters.
- Migration `0008` adds argument, scope and `search_path` checks to the security definer read functions and refuses to run while the application role may create objects in their schemas; migration `0009` adds client network allowlists to API keys (`allowed_networks`, `lorebase apikey create --allow-network`, behind `keeper.trusted_proxies`).
- Bundle import is bounded and refuses links, schema inference sources are configured per Domain, the OIDC issuer and signing keys need `https`, CSV Sources check the resolved address and open files without following links, failed authentications are rate limited per client address and key prefix, the Helm NetworkPolicy is on by default with narrow egress, provider error text is scrubbed, and open event streams are authorized again at an interval.

### Not done yet

### Upgrade notes

There is no earlier release. For a new installation, run the migrations (`alembic upgrade head`, migrations `0001` to `0012`) before Keeper starts: the compose `migrate` service and the Helm hook do it. Migration `0011` creates the `btree_gin` extension when it is missing (it ships with Postgres contrib); on a database that already holds data it builds the search indexes concurrently per partition, without blocking writes. Keeper's shipped configuration accepts every request as an administrator (`keeper.auth.mode: none`); use `api_key` or `oidc` for anything shared, give `api_key` modes a pepper of at least 32 characters, list the administrator in `keeper.auth.installation_admins` and create the first key with `python -m lorebase_keeper bootstrap`.
